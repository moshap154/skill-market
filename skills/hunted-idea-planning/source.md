# idea-planning

AI エージェントに「チャットボットを入れたい」「社内の勉強会を始めたい」のような企画を頼むと、資料はよく読みます。数字から原因を突き止め、すでにある機能や制度、前に試して止まった記録も拾います。外すのは、そのあとの絞り方です。何のための企画かを書かないまま、最初に思いついた形を1つ作り込みます。形の違う案や、やらない案やもっと小さくする案とは比べません。やるかどうか、どの形にするかといった大きな選択も自分で決めてしまい、頼んだ人に返すのは日時や担当のような細部だけになります。

idea-planning は、新しい取り組み・施策・イベント・社内の仕組み・道具の導入の企画を、AI に設計や実装の手前で考えさせる、AI が読む手順書（Skill）です。Skill は、エージェントが作業に合わせて読み込む手順書のファイルです。企画の型（5W1H、SWOT など）は AI がすでに知っているので、型の一覧は入れていません。入っているのは進め方で、目的を1文で置く、形の違う案とやらない案を比べる、勧める案（推し）を添えて、頼んだ人が決めることを返す、の3つが中心です。

向いているのは、まだ何を作るか決まっていない段階で、AI に企画の叩き台を頼む人です。作ると決まったものの仕様を詰める、やる順を決める、といった場面では使いません。

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。入れておくと、エージェントは Skill の説明文（どんなときに読むか）を見て、次のような頼みで読み込みます。

- 「問い合わせが増えたので、チャットボットを入れたい。企画を考えて」
- 「社内で勉強会を始めたい」
- 「忘年会の企画をお願い」

エージェントが読み込むかどうかは、エージェントがその場面だと気づくかどうかで決まります。確実に読ませたいときは「idea-planning の Skill に従って」と名前で頼みます。

## Skill を入れずに頼むと

架空の場面で、Skill を入れない AI に同じ頼みを3回ずつさせました（場面の中身と数え方は、下の「試した結果」）。

- 資料の確かめは強く、2つの場面で3回ずつ、計6回とも原因と前提の食い違いを見つけました。問い合わせの増加が請求書の案内漏れから来ていること、すでにある請求書のダウンロード機能、去年の勉強会が4回で止まった理由、参加したい人が40人中12人しかいないこと、の4つです。頼まれた手段（チャットボット）にも引きずられませんでした。
- 一方で、6回とも、目的を1文で書きませんでした。また6回とも、1つの案を作り込むだけで、形の違う案ややらない案と比べませんでした。勉強会の場面では、形式もテーマも AI が決め、頼んだ人に返したのは開催の時間帯や運営の担当でした。
- 企画書は 53〜107 行になりました。

## SKILL.md に書いてあること

AI が読むファイルです。使うだけなら読まなくてかまいません。どう動くかを確かめたいときは [SKILL.md](../skills/idea-planning/SKILL.md) を開いてください。

- 頼みの手段の向こうにある困りごとを「〜を〜にしたい」の1文にして、企画の最初に書きます。頼みや資料から読み取れれば聞かずに置き、目的しだいで推しが変わるときだけ1つ聞きます。聞くときも、いちばんありそうな目的で作った案を一緒に返します。
- 頼みの中の前提（「倍になった」「みんなやりたがっている」）を数字と照らし、前に同じことをやった記録や、すでにある機能・制度・道具を探します。
- 目的に届く道を、形の違うもの（作る、今あるものを直す、やり方を変える、人や時間を足す）から2〜4つ出します。その中に、やらない案かもっと小さくする案を1つ入れます。
- 効き目・費用と時間・戻せるかで比べて推しを1つ出し、やるかやらないか、どの形にするかは、推しを添えて「決めてほしいこと」として返します。
- 最初の小さな試しと、効いたかを何で見るか、続けるかやめるかの線を書きます。
- 企画は1枚に収めます。長い日程表や案ごとの細かい計画は、推しが決まってから書きます。
- 目的も条件も決まった小さな頼み（日時と予算が決まった懇親会など）では、目的を問い直したり、やらない案を無理に足したりしません。

## 試した結果

2026年11月に、架空の場面で試しました。作業する AI（Claude の Sonnet）は、資料のファイルが入ったフォルダーの中で、ファイルを読み書きしながら企画を作ります。頼む人の役は別の AI が、決めた設定のとおりに演じました。記録は、Skill の有無を伏せて、別の AI（Claude の Opus）が採点しました。場面ごとに守ってほしいこと（観点）を決め、それぞれを満たしたかを見ました。

- 場面1：小さな SaaS の会社のサポートの課長が「問い合わせが去年の倍になり、担当の2人で回しきれない。AI のチャットボットを入れたい」と頼む。資料には、問い合わせの件数、請求書の郵送をやめたお知らせ、マイページの機能の一覧、問い合わせの例、チャットボットの見積もりがある。増えたのはほぼ請求書の再発行で、お知らせに PDF の置き場が書かれていないのが原因。ダウンロードの機能はすでにある。観点は8個。
- 場面2：開発部のマネージャーが「エンジニア向けの社内の勉強会を始めたい。みんなやりたがっている」と頼む。アンケートでは参加したい人は40人中12人、いちばんの困りごとは時間が取れないこと。去年の勉強会は業務時間外の開催と発表者の固定で4回で止まっている。業務時間内に週2時間まで学べる制度がある。観点は8個。
- 場面3：日時・人数・予算・店の候補・去年の感想をまとめたメモを渡して「部の忘年会の企画を」と頼む。落とし穴の無い場面で、Skill を入れたせいで遅くなったり、問い直しが増えたりしないかを見る。観点は6個。

観点は、たとえば場面1なら「目的を確かめるか置くかしてから考えた」「増えたのが請求書の再発行だと突き止めた」「形の違う案を2つ以上比べてから推しを出した」「企画が読める長さ」のようなものです。表の数字は、満たした観点の数を3回分足したものです。分母は観点の数×3回です。採点は観点ごとに「満たした・一部だけ・満たさない」の3段で、表は「満たした」だけを数えています。観点は Skill の書き手が決めたもので、観点ごとの重みは同じに置いています。

| 場面 | Skill なし | Skill あり |
|---|---|---|
| 1 チャットボットを入れたい | 16/24 | 23/24 |
| 2 勉強会を始めたい | 14/24 | 24/24 |
| 3 忘年会（落とし穴なし） | 18/18 | 18/18 |

- 「Skill あり」は、Skill の本文を必ず読ませた条件です。読み手の指摘で言い回しを直す前の版で測りました。
- Skill を置くだけにして、読むかどうかを AI に任せた条件も、場面ごとに3回試しました（作者が使っているほかの Skill 29本と一緒に置いた状態）。9回ともこの Skill を読み、観点は全部満たしました（3回目は、読み手の指摘で本文の言い回しを直したあとの版です）。企画でない頼み（版の公開、本番へのデプロイ）では読みませんでした。
- Skill ありの企画書は 39〜47 行で、Skill なし（53〜107 行）より短くなりました。調べた事実（原因、既存の機能、去年の記録）は、どちらも同じように入っていました。
- 場面を最初から最後まで1回通すのにかかった額は、場面1が Skill なしで 0.075 ドル、ありで 0.076 ドル、場面2が 0.060 ドルと 0.093 ドル（ありの1回は、目的を確かめる問いを1つ挟んで2往復になりました。このあと、聞くときも案を一緒に返すよう本文を直しました。直したあとの版は「置くだけ」の3回目で測り、どの場面も1往復で終わりました）、場面3が 0.045 ドルと 0.049 ドルでした。落とし穴の無い場面3では、かかった時間もほぼ同じでした。
- 場面ごとに3回ずつで、数は少ないです。どの場面も、頼む人とのやり取りは1〜2往復でした。作業する AI が Sonnet 以外のとき、Claude Code 以外のツールで読み込まれるか、何往復も話しながら広げる企画の打ち合わせでどうなるかは、確かめていません。

## 入れ方

```
npx skills add itoken-lab-jp/skills -g --skill idea-planning
```

`-g` は、プロジェクトごとではなく、自分のユーザーのどのプロジェクトでも使える場所に入れる指定です。手順の本文は [SKILL.md](../skills/idea-planning/SKILL.md) です。入れ方の詳しい説明（置かれる場所、ツールごとの違い）は [README](../README.md#入れ方) にあります。
