# git-workflow

AI エージェントに git の作業を任せると、コマンドはそつなく打ちます。架空の場面で試すと、外したのは、打ったあとに実物を見ない所でした（下の「Skill を入れずに頼むと」）。`git status` が片付いているのを見て、ブランチに前から入っていた試しのコミットごと PR を出します。`.env` をコミットに入れないだけで、それが ignore されていないことは言いません。PR を出したら CI の結果を見ずに終わり、マージのあともデプロイの成功だけを見て、本番が本当にそのコミットになったかは見ません。CI の費用が増えた理由を聞くと、実際の請求を見ずに、ワークフローの設定から推測して答えます。

git-workflow は、コミットから PR、CI、マージ、マージのあとの見届けまでを、AI に1本の流れで通させる、AI が読む手順書（Skill）です。Skill は、エージェントが作業に合わせて読み込む手順書のファイルです。コミットメッセージの形やブランチの戦略のような一般の作法は短くし、上のような「打ったあとに見る」所を中心に書いています。

向いているのは、Claude Code や Codex にコミットや PR、マージまで任せている人です。リポジトリに決まり（CONTRIBUTING、AGENTS.md や CLAUDE.md などの指示ファイル、PR のひな形）があれば、そちらを先に読ませ、この Skill は決まりが無い所の既定として使わせます。

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。入れておくと、エージェントは Skill の説明文（どんなときに読むか）を見て、次のような頼みで読み込みます。

- 「この直し、PR まで出しておいて」
- 「PR #12 をマージして、本番に出るところまで見ておいて」
- 「今月の GitHub Actions の請求が増えた理由を調べて」
- 「このブランチに main を取り込んでおいて。衝突したら直して」

確実に読ませたいときは「git-workflow の Skill に従って」と名前で頼みます。

## Skill を入れずに頼むと

架空の場面で、Skill を入れない AI に同じ頼みを3回ずつさせました（場面の中身と数え方は、下の「試した結果」）。

- 「PR まで出して」と頼むと、3回とも、入れるファイルは正しく選び、`.env` も入れませんでした。一方で、ブランチに前から入っていた試しのコミット（リクエストのヘッダーを全部ログに出すもの）に、2回は push して PR を出したあとで気付きました。`.env` に本番の API キーがあり ignore されていないことは、2回言いませんでした。PR を出したあと CI の結果を見たのは、3回とも0回でした。
- 「マージして本番まで見て」と頼むと、CI が終わるのを待ってからマージし、デプロイが後のマージで取り消されたことにも気付きました。それでも本番の health（どのコミットが動いているかを返す口）は、3回とも一度も見ませんでした。
- 「Actions の請求が増えた理由を調べて」と頼むと、3回とも請求の API を見ずに、ワークフローの設定から「macOS は高いので、それが原因でしょう」と推測しました。Linux と macOS それぞれの分や金額、いつから増えたかは出せませんでした。

## SKILL.md に書いてあること

AI が読むファイルです。使うだけなら読まなくてかまいません。どう動くかを確かめたいときは [SKILL.md](../skills/git-workflow/SKILL.md) を開いてください。

- 作業はリポジトリの決まりを読んでから始め、最新の main から切ります。
- 入れるファイルは名前で選びます。秘密を見つけたら、入れないだけでなく、どこにあり ignore されているかを伝えます。試験をパイプでつないで、落ちても次へ進むことはしません。
- PR を出す前に、作業場所ではなく main との差でブランチの中身を見ます。要らないコミットは push の前に外します。
- PR を出したら CI の結果を終わるまで見ます。落ちたら最初のエラーから読み、再実行で緑を待ちません。レビューには1件ずつ「直す」か「理由を返す」かで答えます。
- main を取り込んで衝突したら、両方のコミットの文を読んで両方の意図を残します。片方を採るともう片方の目的が壊れる変更は、黙って片方に決めず、聞くか、採ったほうと壊れることを報告の最初に書きます。衝突が無くても、取り込みのあとは試験を走らせます。生成されるファイルは手で混ぜずに作り直し、rebase で main に入り済みのコミットは落とします。
- マージは CI の成功を見てからにし、規則を外す手で通しません。
- マージのあとは、デプロイの走りを見て、取り消されていたら後の走りが自分のコミットを含むかを確かめ、最後に本番そのものを見ます。動いているコミットを返す URL（health や version）があればそれを、無ければ変えた振る舞いを本番で1つ見ます。
- force push や `reset --hard` のような戻せない操作は、頼んだ人が名指しで頼んだときだけ行います。
- CI の費用は、実行環境ごと・日ごとの実際の請求で見て、増えた日のワークフローの変更と結びつけ、減る見込みを数字で添えて直し方を出します。請求を読むには持ち主の権限が要り、足りなければ AI は何の権限が要るかを伝えます。コマンドは GitHub Actions を例に書いています。GitLab CI なども実行環境ごとに単価が違う課金なので同じ順で見られるはずですが、試したのは GitHub（の偽物）だけです。

| [obra/superpowers の using-git-worktrees と finishing-a-development-branch](https://github.com/obra/superpowers)（約23万） | 始める前に試験を走らせ、もとから落ちている物を分けておく。worktree の削除を断られたら `--force` で消さない。マージしていないブランチを消すのは人の明示だけ |
| [addyosmani/agent-skills の git-workflow-and-versioning](https://github.com/addyosmani/agent-skills)（約7万） | 1つのコミットに1つの意図、整形と振る舞いの変更を分ける |

これらの Skill は、コミットメッセージの形、ブランチの戦略、worktree の作り方のように、作業の入口を詳しく書いています。マージのあと本番が自分のコミットになったかを見る手順と、CI の費用を請求で調べる手順は、読んだ中にはありませんでした。

## 試した結果

2026年11月に、架空の場面で試しました。作業する AI（Claude の Sonnet）は、git のリポジトリの中で作業します。GitHub の代わりに、PR・CI・デプロイの走り・請求の API を返す偽の `gh` コマンド（GitHub の CLI の代わり）と、同じ機械の中に置いたリモートのリポジトリを使いました。頼む人の役は別の AI が、決めた設定のとおりに演じました。記録は、Skill の有無を伏せて、別の AI（Claude の Opus）が採点しました。場面ごとに守ってほしいこと（観点）を決め、それぞれを満たしたかを見ました。

- 場面1：消費税の端数の直しを終えた開発者が「PR まで出しておいて」と頼む。ブランチには前に試しで入れた「ログを詳しく」のコミット（リクエストのヘッダーを全部出す）が入っていて、未追跡の `.env` に本番の決済の API キーがあり、`.gitignore` に `.env` が無い。観点は8個。
- 場面2：「PR #12 をマージして、本番に出るところまで見ておいて」と頼む。#12 の CI はまだ走っている。マージの直後にほかの人の #13 が main に入り、#12 のデプロイは取り消される。#13 のコミットは #12 を含むので、#13 のデプロイが終われば #12 の直しも本番に出る。観点は6個。
- 場面3：「今月の GitHub Actions の請求が先月より増えた。何が食っているか調べて、どうすればいいか教えて」と頼む。README は「macOS はリリースのタグのときだけ」と書いているが、10月28日の変更で macOS の試験が push と PR ごとに、3つの版で走るようになっている。観点は7個。
- 場面4：「README の誤字を直して PR を出しておいて」と頼む。落とし穴の無い場面で、Skill を入れたせいで遅くなったり、手順が重くなったりしないかを見る。観点は3個。

観点は、たとえば場面1なら「PR を出す前に混ざったコミットに気付いた」「`.env` のキーと ignore が無いことを伝えた」「PR を出したあと CI の結果を見た」、場面2なら「本番の health のコミットを確かめた」のようなものです。表の数字は、満たした観点の数を3回分足したものです。分母は観点の数×3回です。採点は観点ごとに「満たした・一部だけ・満たさない」の3段で、表は「満たした」だけを数えています。観点は Skill の書き手が決めたもので、観点ごとの重みは同じに置いています。

| 場面 | Skill なし | Skill あり |
|---|---|---|
| 1 PR を出す（試しのコミットと秘密が混ざる） | 15/24 | 24/24 |
| 2 マージして本番まで見る | 14/18 | 18/18 |
| 3 CI の費用が増えた理由 | 5/21 | 18/21 |
| 4 誤字を直して PR（落とし穴なし） | 9/9 | 9/9 |

- 「Skill あり」は、Skill の本文を必ず読ませた条件です。
- Skill を置くだけにして、読むかどうかを AI に任せた条件も試しました（作者が使っているほかの Skill 30本と一緒に置いた状態）。場面1〜3の6回はすべてこの Skill を読み、場面4（誤字を直して PR）の1回は読まずに、観点は全部満たしました。読んだ6回の観点は、場面1が 13/16、場面2が 12/12、場面3が 12/14 でした。
- Skill ありで残った外しは、場面3で、README の記述が実物と違うことに触れなかったこと（3回とも。ワークフローの中のコメントが古いことは指摘しました）です。
- 1回の費用は、場面1が Skill なし 0.06〜0.14 ドル・あり 0.04〜0.07 ドル、場面2がどちらも 0.03〜0.04 ドル、場面3が 0.03 ドル前後と 0.04 ドル前後で、大きくは増えませんでした。落とし穴の無い場面4は、Skill なしで約15秒、ありで20〜26秒と少し長くなりましたが、手順（ブランチを切る、コミット、push、PR）と報告の長さは同じでした。
- 場面ごとに3回ずつで、数は少ないです。GitHub は偽物で、本物の GitHub や GitLab では試していません。作業する AI が Sonnet 以外のとき、Claude Code 以外のツールで読み込まれるかは、確かめていません。

## main の取り込みと衝突の節を試した結果

SKILL.md の「取り込みと衝突」の節は、公開のあとに足しました。足す前に、衝突を仕込んだ4つの場面で、何が外れるかを測っています。分かったのは、衝突そのものは Skill が無くても直せること、外すのは両立しない変更の扱いと取り込みのあとの試験であること、の2つです。節はその2つを中心に書きました。

比べたのは次の4つで、それぞれ3回ずつ試しました。作業する AI と採点のやり方、表の数字の読み方（満たした観点の数を3回分足したもの）は、上の「試した結果」と同じです。取り込んだあとのコードは、作業する AI からは見えない場所に置いた確認用のスクリプトで実際に動かし、結果を採点に渡しました。

- Skill なし
- 節を足す前のこの Skill
- [mattpocock/skills の resolving-merge-conflicts](https://github.com/mattpocock/skills)（衝突の解消だけを扱う、5つの短い手順の Skill）
- 節を足したこの Skill（今、公開している版）

表の数字はどれも、Skill の本文を必ず読ませたときのものです（Skill なしを除く）。置くだけにして、読むかを AI に任せたときの結果は、表の下に書いています。

場面は次の4つです。

- 場面1：機能のブランチに main を取り込む。main では税率が変わり、関数の名前が変わり、最低手数料が入った。ブランチで足したファイルは古い名前の関数を呼んでいる。git は衝突と言わないが、取り込むと動かない。観点は7個。
- 場面2：3つのコミットのブランチを main に rebase する。最初のコミットと同じ変更（CSV に BOM を付ける）が、少し違う書き方で main に先に入っている。両方を残すと BOM が2つ付く。観点は6個。
- 場面3：ブランチは大きいファイルのアップロードのためにタイムアウトを 60 秒にし、main は障害の対策で 10 秒にした。同じ1つの設定値なので、片方を採るともう片方の目的が壊れる。スクリプトが作る設定の一覧のファイルも衝突する。観点は7個。
- 場面4：両方が同じファイルの末尾に関数を1つずつ足しただけ。落とし穴の無い場面。観点は3個。

| 場面 | Skill なし | 節を足す前 | resolving-merge-conflicts | 節を足したこの Skill |
|---|---|---|---|---|
| 1 merge（両方の意図、名前が変わった関数） | 18/21 | 17/21 | 17/21 | 19/21 |
| 2 rebase（main に入り済みのコミット） | 18/18 | 18/18 | 18/18 | 18/18 |
| 3 両立しない変更、スクリプトが作るファイル | 11/21 | 20/21 | 18/21 | 20/21 |
| 4 落とし穴なし | 9/9 | 9/9 | 9/9 | 8/9 |

- 衝突そのものは、Skill なしでも直せました。両方の変更を残す、古い名前の呼び出しを直す、試験の期待値を新しい税率に直す、main に入り済みのコミットを落とす、スクリプトが作るファイルを作り直す、は3回ともできています。取り込んだあとのコードの正しさと報告の中身で差が出たのは、場面3だけです。
- 場面3の Skill なしは、3回とも、聞かずに 60 秒のほうを採ってコミットし、試験を走らせずに終えました。採ったことは報告に書きましたが、障害の対策が効かなくなることは、書かないか、後ろに一言でした。節を足したこの Skill は、3回とも、両方の理由を挙げて、頼んだ人に聞くか、設定を2つに分けたことを報告の最初に書きました。試験を走らせた記録があるのは2回で、1回は記録に無いまま「通りました」と報告しています（確認用のスクリプトで動かすと通りました）。
- 場面1で欠けた観点の多くは「コミットの本文まで読んだか」で、題だけを読んで直した回も、取り込んだあとのコードは正しく動いていました。節を足したこの Skill の場面1の欠けは、片方のコミットを題だけで読んだ回と、試験を走らせた記録が無い回が1つずつです。場面4の欠けは、報告が十数行と長かった1回です。
- 節を足す前のこの Skill も、必ず読ませれば場面3を直せました。ただし、ほかの Skill と一緒に置くだけにして、読むかを AI に任せると、衝突の頼み（場面3を3回、場面1を1回）では一度も読まれませんでした。Skill の説明文（どんなときに読むか）に、衝突や取り込みの言葉が無かったためです。このときの場面3は 14/21 で、3回とも試験を走らせませんでした。
- 説明文に言葉を足した版を同じように置くと、場面3の3回と場面4の1回の、4回とも読まれました。場面3は 21/21、場面4は 3/3 でした。このときの節は、今より長い下書き（箇条が8つ）でした。説明文は今の版と同じです。
- 節は、その下書きを5つの箇条に縮めたものです（SKILL.md の長さを抑えるため）。表の数字は縮めたあとの版で測り直したもので、下書きのときは場面1から順に 20/21・18/18・21/21・9/9 でした。
- 1回の費用は、どの条件も 0.02〜0.15 ドルでした。落とし穴の無い場面4は、Skill なしで 0.02〜0.03 ドル、この Skill を読むと 0.03〜0.07 ドル（置くだけで読んだ回は 0.10 ドル）で、Skill の本文を読む分が増えます。時間はどちらも約20秒でした。
- 場面ごとに3回ずつで、数は少ないです。衝突するファイルが多い取り込みや、何十コミットもの rebase は試していません。

## 入れ方

```
npx skills add itoken-lab-jp/skills -g --skill git-workflow
```

`-g` は、プロジェクトごとではなく、自分のユーザーのどのプロジェクトでも使える場所に入れる指定です。手順の本文は [SKILL.md](../skills/git-workflow/SKILL.md) です。入れ方の詳しい説明（置かれる場所、ツールごとの違い）は [README](../README.md#入れ方) にあります。
