# ticket-writing

AI に「仕様を作業の票に分けて Issue を立てておいて」と頼むと、票はすぐに立ちます。架空の場面で Skill を入れない AI に試させると、外したのは書く前に集める所と分け方でした（下の「Skill を入れずに頼むと」）。仕様のファイルだけを読み、頼みの元の Issue のコメントで後から覆った決定を見落としました。コードを読まず、DB・API・画面の層ごとに割った票を、順も済んだと言える条件も無しに立てました。DB の列の改名を頼むと、止めずに出す（新旧のコードが同じ DB を同時に使う）運用なのに列を一度に改名する順にし、外のシステムが読む CSV の列名まで変える票を立てました。チャットの話を仕様にする場面では、覆った決定や未決は Skill なしでも正しく拾い、差は小さめでした。

ticket-writing は、仕様・会話・メモ・大きな頼みを、作業の票（GitHub の Issue、Jira・Backlog・Redmine などのチケット）に AI に書かせる・分けさせるときの、AI が読む手順書（Skill）です。Skill は、エージェントが作業に合わせて読み込む手順書のファイルです。票は、書いた人がいない所で別の人や AI が拾って作るものなので、拾った人が調べ直さずに済み、どこまで作れば済みかが分かり、途中で壊さずに出せる票を書かせます。「立てておいて」と頼まれれば、AI は票を実際に立て、元の Issue からたどれるようにリンクやコメントを付けます。元の Issue を閉じたり本文を書き換えたりはしません。

向いているのは、Claude Code や Codex に Issue やチケットを書かせている人、票を別の人や AI に拾わせている人です。チームやリポジトリに票の決まり（ひな形・ラベル・粒度）があれば、そちらを先に読ませ、この Skill は決まりが無い所の既定として使わせます。

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。入れておくと、エージェントは Skill の説明文（どんなときに読むか）を見て、次のような頼みで読み込みます。

- 「#21 の仕様、作業の票に分けて Issue を立てておいて」
- 「チャットで話したこの件、仕様にまとめて Issue を1つ立てて」
- 「この列の名前を全部変えたい。チケットに起こして」

確実に読ませたいときは「ticket-writing の Skill に従って」と名前で頼みます。

## Skill を入れずに頼むと

架空の場面で、Skill を入れない AI に同じ頼みを3回ずつさせました（場面の中身と数え方は、下の「試した結果」）。

- 「仕様を票に分けて」と頼むと、3回とも、元の Issue のコメント（「PDF は作り直さず、最初に送った物を付ける」と決まっていた）を読まず、古い仕様のまま「PDF を作り直す」票を立てました。3回ともコードを開かず、DB・API・画面・監査ログなどの層ごとに4〜5票へ割り、どの票が先かと、済んだと言える条件は、書かないか一部だけでした。決まっていない上限の回数は、3回とも決めずに残しました。
- 「顧客コードの列を全部改名する票に」と頼むと、3回とも、止めずに出す（新旧のコードが同じ DB を同時に使う）運用なのに、列を一度に改名する順にしました。経理の会計ソフトが列名で読む CSV の列名も、3回とも変える票に入れていました。うち2回は、外に影響すると票に書いてはいました。
- 「チャットで話したことを仕様にして」と頼むと、覆った決定（前日18時→当日朝8時）、やらないこと、未決は3回とも正しく拾いました。一方で3回ともコードを読まず、今の予約の状態や送信の仕組みに結びつかない仕様になりました。
- 「作業中の PR があり、知らせ方が後のコメントで変わった」場面（Skill を書いたあとに作った場面）では、知らせ方の変更は拾いましたが、3回とも、作業中の PR を Issue の番号として探して見つけられず（PR の一覧は見ませんでした）、コードも読みませんでした。

## SKILL.md に書いてあること

AI が読むファイルです。使うだけなら読まなくてかまいません。どう動くかを確かめたいときは [SKILL.md](../skills/ticket-writing/SKILL.md) を開いてください。

- 書く前に、元の票の本文だけでなくコメントと紐づく PR まで読み、仕様と食い違えば後の決定を採って、どちらを採ったかを書きます。関わるコードを読み、使える関数・表・権限の仕組みを票に名前で書きます。外に約束している名前と、出し方（止めずに出すか）も見ます。
- 会話やメモから仕様にするときは、最後に決まった形で書き、決まったこと・やらないこと・決まっていないことを分け、話に出ていないことは「提案」として分けます。
- 1票は、使う人から見て1つの動きが確かめられる単位にし、層ごとには割りません。最初の票は端から端まで通る最小の形にします。小さい変更は1票にし、割りません。各票に先に済んでいるべき票を書きます。
- 全体に及ぶ改名は、足す（両方使える）→ 束ごとに移す → 消す、の順にし、どの票のあとも試験が通るようにします。外に約束している名前は変えないか、別の票にして頼んだ人に確かめます。
- 各票に、なぜ・やること・済んだと言える条件・先に済むもの・決まっていないことを書きます（ひな形つき）。
- 決まっていないことは自分で決めず、決まるまで作れない部分を「待ち：誰の何」の票に分けます。
- 元の票は閉じず、本文を書き換えず、新しい票から元の票へつなぎます。

| 取り入れた所 | 取り入れなかった所 |

| 層ごとでなく端から端まで通る細い単位に切る、票ごとに先に済むべき票を書く、作業を楽にする作り替え（リファクタリング）を先の票にする、全体に及ぶ改名は足す・移す・消すの順にする、ファイルのパスは古くなるので書きすぎない | 長いユーザーストーリーの一覧、分け方を人が承認するまで聞き続ける往復、同じリポジトリのほかの Skill で行う初期設定を前提にする所、決まったラベル |

## 試した結果

2026年11月に、架空の場面で試しました。作業する AI（Claude の Sonnet）は、git のリポジトリの中で作業します。GitHub の代わりに、Issue と PR を返す偽の `gh` コマンド（GitHub の CLI の代わり）と、同じ機械の中に置いたリモートのリポジトリを使いました。頼む人の役は別の AI が、決めた設定のとおりに演じました。記録は、Skill の有無を伏せて、別の AI（Claude の Opus）が採点しました。場面ごとに守ってほしいこと（観点）を決め、それぞれを満たしたかを見ました。

- 場面1：請求書の再送の仕様（docs のファイル）を票に分ける。元の Issue のコメントで PDF の扱いが覆っていて、再送の上限は未決。観点は8個。
- 場面2：顧客コードの列を全部改名する票に分ける。止めずに出す運用で、売上の CSV と公開の API は外が読んでいる。観点は7個。
- 場面3：チャットの写しから予約のリマインドの仕様を書き、Issue を1つ立てる。送る時刻が途中で覆り、LINE はやらないことになり、文面と配信停止は未決。観点は7個。
- 場面4：README に Windows の手順を足す票を1つ立てる。落とし穴の無い場面で、Skill を入れたせいで分けすぎたり重くなったりしないかを見る。観点は3個。
- 場面5：在庫の知らせを票に分ける。発注点の判定は作業中の PR がすでに作っていて、知らせ方が後のコメントでメールから Slack に変わり、Slack のチャンネルは未決。Skill を書いたあとに、書くときに見ていない場面として作りました。観点は7個。

観点は、たとえば場面1なら「元の Issue のコメントの決定を拾った」「どの票もそれだけで動きを確かめられる」「各票に先に済む票と済んだと言える条件がある」、場面2なら「足す・移す・消すの順にした」「外が読む名前に気付いた」のようなものです。表の数字は、満たした観点の数を3回分足したものです。分母は観点の数×3回です。採点は観点ごとに「満たした・一部だけ・満たさない」の3段で、表は「満たした」だけを数えています。観点は Skill の書き手が決めたもので、観点ごとの重みは同じに置いています。独立に試したのは場面ごとに3回なので、24/24 は「3回とも全部の観点を満たした」という意味です。

| 場面 | Skill なし | Skill あり |
|---|---|---|
| 1 仕様を票に分ける（コメントで覆った決定と未決） | 6/24 | 24/24 |
| 2 全体に及ぶ改名を票に分ける | 4/21 | 21/21 |
| 3 チャットを仕様にする | 18/21 | 20/21 |
| 4 Windows の手順の票（落とし穴なし） | 6/9 | 8/9 |
| 5 在庫の知らせを票に分ける（Skill を書いたあとに作った場面） | 10/21 | 21/21 |

- 「Skill あり」は、Skill の本文を必ず読ませた条件です。場面1〜4は、Skill なしの外し方を見てから Skill を書いたので、Skill がその場面に合わせて書かれている分、数字は甘く出ている可能性があります。場面5は、書いたあとに作った場面です。
- Skill を置くだけにして、読むかどうかを AI に任せた条件も試しました（作者が使っているほかの Skill 30本と一緒に置いた状態）。場面1・2・3・5の7回はすべてこの Skill を読み、観点は全部満たしました（場面1が 16/16、場面2が 14/14、場面3が 7/7、場面5が 14/14）。場面4（落とし穴なし）の1回は読まずに、観点は全部満たしました。
- Skill ありで残った外しは、場面3の1回で、提案として分けると書いた条件を済んだ条件の側にも入れたこと、場面4の1回で、中身の書き込みが一部足りなかったことです。
- 1回の費用（Skill なし → あり）は、場面1が 0.03 → 0.08〜0.09 ドル、場面2が 0.05〜0.10 → 0.10〜0.13 ドル、場面3が 0.03 → 0.05 ドル、場面4が 0.01〜0.02 → 0.03 ドル、場面5が 0.03 → 0.09 ドルで、多くは2〜3倍になりました。コメントや PR、コードを読む分です。落とし穴の無い場面4の時間は、Skill なしで14〜16秒、ありで23〜25秒でした。
- 場面ごとに3回ずつで、数は少ないです。GitHub は偽物で、本物の GitHub や Jira・Backlog では試していません。作業する AI が Sonnet 以外のとき、Claude Code 以外のツールで読み込まれるかは、確かめていません。

## 入れ方

```
npx skills add itoken-lab-jp/skills -g --skill ticket-writing
```

`-g` は、プロジェクトごとではなく、自分のユーザーのどのプロジェクトでも使える場所に入れる指定です。手順の本文は [SKILL.md](../skills/ticket-writing/SKILL.md) です。入れ方の詳しい説明（置かれる場所、ツールごとの違い）は [README](../README.md#入れ方) にあります。
