# test-workflow

AI に不具合を直させると、テストを一度も走らせないままコードとテストを同時に直し、「テストを足して、全部通りました」と報告することがあります（下の「試した結果」では3回中3回）。この順だと、足したテストが直す前の不具合で落ちるか、つまり不具合を本当に捕まえているかが分かりません。変える前の状態を知らないので、もともと落ちていたテストを自分の変更のせいと取り違えることもあります。test-workflow は、AI にテストを書かせる・走らせる・直させるときにエージェントが読む Skill（手順書の `SKILL.md`）です。

## 使い方

入れたあとは、ふだんどおりに頼みます。

> 請求書の税込合計が1円ずれるので直して

> テストが遅いので速くして

エージェントは、変える前にテストを一度走らせ、もともと落ちているテストと、全部にかかる時間を確かめます。不具合を再現するテストを足して、そのテストが落ちる（赤になる）のを見てから直し、作業中は変えた所に効くテストだけを走らせます。通ったあとは、CLI や API を実際に動かして結果を見ます。

## SKILL.md に書いてあること

AI が読むファイルです。どう動くかを確かめたいときは [SKILL.md](../skills/test-workflow/SKILL.md) を開いてください。

- 始めるとき：変える前に一度テストを走らせ、走らせ方・件数・時間・もともと落ちているテストを知る。共有の DB や本物の外部サービスに書き込むテストは、書き込み先がテスト用だと確かめるまで走らせない。もともと落ちているテストは、黙って直さず報告する。
- 書くとき：中身の作りではなく外から見た振る舞いを確かめる。直す前に、足したテストが落ちるのを見る。時刻・乱数・データの並びの順を固定して、毎回同じ結果にする。走らせるたびに結果が変わる（揺れる）テストを、通るまで回し直して済ませない。対象（計算の関数・データの処理・DB・外部の API・CLI・画面）ごとの試し方の表もあります。
- 走らせ方：作業中は変えた所に効くテストだけを走らせる（pytest・node・vitest・go・cargo のコマンドの例つき）。1件が軽いテストに、並列（pytest-xdist の `-n`）を測らずに付けない。
- 通ったあと：CLI は境目の値で、Web の API は開発用のサーバーを立てて、画面は撮って、実物を動かす。見つけた不具合はテストにして残す。
- テストを消させない：テストを消す・skip にする・mock に置き換える・期待を書き換える（スナップショットの一括更新を含む）のは、仕様が変わったときだけ。エージェントが PR を見るときも、差分でこの点を見る。

リポジトリにテストのコマンドや分け方の決まり（AGENTS.md・README・CI の設定）があれば、エージェントはそちらに従います。この Skill は、決まりが無い所の既定です。

## 試した結果

2026年11月に、小さな架空のリポジトリで2つの場面を作り、Skill を入れたときと入れないときで3回ずつ試しました。作業する AI（Claude の Sonnet）は、リポジトリの写しの中でコマンドを実行し、ファイルを直してコミットします。頼んだ人の役は別の AI（Sonnet）が演じました。作業の記録は、Skill の有無を伏せて、別の AI（Claude の Opus）が採点しました。場面ごとに守ってほしいこと（観点）を6〜7個決め、それぞれを満たしたかを見ました。ただし、場面1の「直したあとに CLI を動かしたか」の観点は、採点に渡した記録で手順が途中で切れていて、採点した AI が3回分を見落としました。そこは作者が作業の全記録で数え直しました（Skill なしの2回と Skill ありの1回を、満たしたに直しました）。この数え直しは、条件を伏せずに行っています。

表の数字は、満たした観点の数を3回分足したもので、分母は観点の数×3回です。

| 場面 | Skill なし | Skill あり |
|---|---|---|
| 1. 請求書の税込合計の1円ずれを直す | 11/21 | 20/21 |
| 2. 全部で30秒かかるテストを速くする | 14/18 | 16/18 |

場面1のリポジトリには、もともと落ちている表示のテストと、税の計算の誤りを前提にした古いテストと、25秒かかる通しの試験を入れておきました。

- Skill なしの AI は3回とも、テストを走らせる前にコードを直し、再現のテストも同時に足しました。足したテストが直す前に落ちるかは見ていません。
- Skill ありの AI は3回とも、先に全部のテストを走らせ、再現のテストを足して落ちるのを見てから直しました。作業中は税の計算のテストのファイルだけを走らせました。
- もともと落ちていた表示のテストに触らず報告することと、古いテストの期待を書き換えた理由を仕様の変更として書くことは、Skill がなくても3回ともできていました。
- 直したあとに CLI を実際に動かして結果を見た回は、Skill なしで3回中2回、Skill ありで3回中3回でした。

場面2は、Skill がなくてもよくできました。どちらも先に時間を測り、試験ごとに DB を作り直していた所を直し、遅い決済の試験は消さずに印を付けて分けました。差は、報告に前後の件数とコマンドを添えたかどうかだけです。Skill なしの1回は、並列（`-n auto`）を `pyproject.toml` のテストの既定の設定に入れました。pytest-xdist が入っていない環境では、テストが走らなくなります。Skill ありの3回は、並列を既定の設定に入れませんでした。

各3回の小さな試験で、場面と観点を作った人と Skill を書いた人は同じです。観点は Skill に書いた手順を守ったかを見るもので、不具合や手戻りが減るかは測っていません。作業する AI は Sonnet だけで、ほかのモデルやツールでは試していません。Skill のあるなしで良くなる向きを見るための数字で、どの現場でもこの割合で効くという意味ではありません。試した版は、公開している版から2つの文（揺れたテストを回し直して済ませない、スナップショットの一括更新も期待の書き換えに含める）を足す前のものです。

## 並列（-n）の測り方

SKILL.md の「1件が軽いテストに `-n` を付けると遅くなる」は、次の測定によります。測った環境は Linux（x64・4コア）・Python 3.13・pytest 9.2・pytest-xdist 3.8 で、2026年11月14日に測りました。3回の中央値です。

| テスト | `-n` なし | `-n 4` |
|---|---|---|
| 1件が1ミリ秒ほどの500件 | 0.72秒・CPU 0.70秒 | 1.10秒・CPU 2.75秒 |
| 1件が0.1秒の40件 | 4.36秒・CPU 0.35秒 | 1.84秒・CPU 1.79秒 |

1件が軽いと、ワーカーを起動する分だけ遅くなり、CPU は約4倍使います。1件が重いテストでは、CPU は余分に使うものの、時間は短くなります。ただし重いテストの代わりに待つだけ（sleep）のテストで測ったので、CPU を使う重いテストや、CPU が空いていない CI では、速くならないことがあります。そのため SKILL.md では、付けるなら前後で測るようにしています。Windows と Mac では測っていません。

手元で測り直すには、Linux か Mac（CPU の時間の測り方が Windows に無いため）に Python 3 と pytest・pytest-xdist を入れて、このリポジトリの `tools/test-workflow/bench_xdist.py` を実行します。テストのファイルはスクリプトが作ります。引数を付けないと上の表の1行目（500件）、2つ目のコマンドが2行目を測ります。

```
python3 tools/test-workflow/bench_xdist.py
python3 tools/test-workflow/bench_xdist.py --tests 40 --sleep 0.1
```

## 入れ方

```
npx skills add itoken-lab-jp/skills -g --skill test-workflow
```

Claude Code・Codex・Cursor・GitHub Copilot・Antigravity に入ります。`-g` は、全部のプロジェクトで使える置き場に入れる指定です。入れ方の詳しい説明は [README](../README.md#入れ方) にあります。
