# web-ui-quality

AI に「申し込みフォームの見た目を整えて」と頼むと、コードの上ではきれいに整います。架空の場面で Skill（AI が読む手順書）を入れない AI に試させると、外したのは、測れば分かる所と、ブラウザで開いて確かめる所でした（下の「Skill を入れずに頼むと」）。白い文字と明るい青のボタン（文字と背景の明るさの比が 3.5。読みやすさの基準の WCAG では 4.5 以上）や 13px の注意書きを残し、未入力のエラーはどの欄が足りないか分からないポップアップ（alert）のままにし、ブラウザで開かずに「実機で一度見てください」と渡しました。

web-ui-quality は、Web の画面（ページ、フォーム、お知らせ、管理画面、データから作るレポートのページ）を AI に作らせる・整えさせるときの、AI が読む手順書（Skill）です。Skill は、エージェントが作業に合わせて読み込む手順書のファイルです。デザインには好みがあるので、色や雰囲気は決めません。読める文字の大きさと色の差、スマホではみ出さないこと、押しやすさ、キーボードで今どこにいるかが見えること、入力欄のラベルとエラーの出し方、日本語の組みといった、誰にとっても悪くない下限をそろえさせ、スマホと PC の幅でブラウザで開いて撮ってから渡させます。

向いているのは、Claude Code や Codex などのエージェントに、HTML・CSS や React の画面を作らせている人です。デザインシステム（色や余白の決まり、部品）があるリポジトリでは、AI はそちらに従い、この Skill は決まりが無い所の既定として使います。ボタンの文言を変えるだけのような小さな直しでは、頼まれた所だけを変えます。

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。入れておくと、エージェントは Skill の説明文（どんなときに読むか）を見て、次のような頼みで読み込みます。

- 「この申し込みフォーム、見た目を整えて。スマホからが多いです」
- 「お知らせの文で、社内向けのページを作って」
- 「売上の CSV から、店長向けのまとめのページを作って」

確実に読ませたいときは「web-ui-quality の Skill に従って」と名前で頼みます。AI が手元でブラウザ（Playwright など）を使えると、撮って測るところまでします。使えないときは、確かめていないと報告に書きます。

## Skill を入れずに頼むと

架空の場面で、Skill を入れない AI に同じ頼みを3回ずつさせました。作ったページは、AI から見えない検査が Chromium（幅 390px と 1440px）で開いて測りました（場面の中身と数え方は、下の「試した結果」）。

- 申し込みフォームを整える場面では、3回とも、ラベルや入力欄の大きさは良くしましたが、送信ボタンの白い文字と青（比 3.5、必要なのは 4.5）と、13px の注意書きを残しました。未入力のエラーは3回とも alert のままで、どの欄が足りないかを欄の近くに出しませんでした。3回ともブラウザで開かずに報告しました。
- 売上の CSV からまとめのページを作る場面（Skill を書いたあとに作った場面）では、3回とも書体を `sans-serif` だけにして日本語の書体を指定せず、2回は7列の表がスマホの幅から横に 149〜196px はみ出し、2回は「未入力」の灰色の文字が薄すぎました。2回は「大きく落ち込んでいます」のような、頼まれていない評価を書き足しました。3回ともブラウザで開きませんでした。
- お知らせのページを作る場面では、行間・文字の大きさ・色の差は3回とも満たしていました。外したのは、ブラウザで確かめなかったこと（3回とも）と、連絡先のメールのリンクの押せる所が高さ 17px と小さいことでした。
- ボタンの文言を1つ変えるだけの場面では、3回とも頼まれた所だけを変えました。

## SKILL.md に書いてあること

AI が読むファイルです。使うだけなら読まなくてかまいません。どう動くかを確かめたいときは [SKILL.md](../skills/web-ui-quality/SKILL.md) を開いてください。

- 作る前に、誰がどこで見るかと、一番伝えたいことを読みます。元の文・数字・ボタンの文言は変えず、元に無い評価も足しません。form の送り先や項目の名前など、外とつながる所も変えません。
- 下限：`lang="ja"` と viewport、幅 320〜390px ではみ出さない。本文 16px、注意書きも 14px 以上、入力欄 16px（iPhone の拡大を防ぐ）。行間 1.7 前後、本文の幅は 40em 前後。文字と背景の比は 4.5 以上（ボタンの文字・placeholder・灰色の補足も）。日本語の書体を名前で並べる。押せる所は 44px を目安に、フォーカスを見えるようにする。色だけで示さない。
- 見た目の整え方：一番伝えたいことと見落とすと困る注意を一番目立たせる、文字の大きさは3段ほど・色は目立たせる色1つほどに絞る、余白は 8px の倍数から3〜5段を使い回す、数字は右にそろえて桁の幅をそろえる、読み込み中・0件・エラーを別の表示にする。
- フォーム：常に見えるラベル、`type` と `autocomplete`、エラーは欄の近くに「何が・どう違い・どう直すか」を文字で出し、`aria-describedby` で結び、最初のエラーの欄にフォーカスを移す。
- 確かめ：幅 390px と 1440px で開いて撮り、はみ出し・文字の大きさ・色の比・小さい押せる所・Tab のフォーカスを測る。フォームは空のまま送って見る。直して撮り直すのは2〜3回までで、好みの差は直し続けず、撮った画像を頼んだ人に見てもらう。測る例（Playwright の短いスクリプト）は [references/check.md](../skills/web-ui-quality/references/check.md) にあります。

数字は、WCAG 2.2、デジタル庁デザインシステム、SmartHR Design System、NN/g の記事を 2026年11月に読んで、そろえた目安です。

## 試した結果

2026年11月に、架空の場面で試しました。作業する AI（Claude の Sonnet）は、元のファイルを置いた git のフォルダーの中で作業します。頼む人の役は別の AI が、決めた設定のとおりに演じました。作業のあと、AI から見えない検査が、作った・直した HTML を Chromium で幅 390px と 1440px で開いて測りました（はみ出し、文字の大きさ、行間、1行の字数、色の比、小さい押せる所、フォーカス、ラベルの無い入力欄）。記録と測った値は、Skill の有無を伏せて、別の AI（Claude の Opus）が採点しました。場面ごとに守ってほしいこと（観点）を決め、それぞれを満たしたかを見ました。

- 場面1：お知らせの文（健康診断）から、社内向けのページを作る。観点は9個。
- 場面2：見た目の悪い申し込みフォーム（Arial の 12px・薄い灰色、幅 600px 固定、placeholder だけの入力欄、alert のエラー）を整える。送り先と項目の名前は変えられない。観点は8個。
- 場面3：フォームのボタンの文言を「送信」から「申し込む」に変えるだけ。落とし穴の無い場面で、Skill を入れたせいで頼まれていない所まで直さないかを見る。観点は3個。
- 場面4：売上の CSV（5店舗×3か月、前年比がマイナスの店と、未集計の空の値がある）から、店長向けのまとめのページを作る。Skill の最初の版を書いたあとに作った場面です。観点は7個。

観点は、たとえば場面2なら「スマホの幅で横にはみ出さない」「色の比が足りない文字が無く、本文が 15px 以上」「未入力の欄を、その欄の近くに文字で知らせる」「ブラウザで開いてスマホと PC の幅で見てから報告した」、場面4なら「数字の列を右にそろえ、単位がある」「未集計を 0 にせず、未集計と分かるようにした」のようなものです。表の数字は、満たした観点の数を3回分足したものです。分母は観点の数×3回です。採点は観点ごとに「満たした・一部だけ・満たさない」の3段で、表は「満たした」だけを数えています。観点と、本文 15px・1行 45 字などの線は Skill の書き手が決めたもので（Skill の本文の目安とは少し違います）、観点ごとの重みは同じに置いています。独立に試したのは場面ごとに3回です。

| 場面 | Skill なし | Skill あり |
|---|---|---|
| 1 お知らせのページを作る | 20/27 | 27/27 |
| 2 フォームの見た目を整える | 15/24 | 23/24 |
| 3 ボタンの文言だけ（落とし穴なし） | 9/9 | 9/9 |
| 4 CSV からまとめのページ（Skill の最初の版のあとに作った場面） | 8/21 | 20/21 |

- 「Skill あり」は、Skill の本文を必ず読ませた条件で、表は2回目の版の数字です。最初の版では、場面1・2・4が 21/27・24/24・18/21 でした。最初の版は、場面2（フォーム）の3回とも頼まれていないボタンの文言を変え（「ボタンの文言は動詞で書く」に従った）、場面4では表の文字をスマホで 14px に縮め、場面1では見落とすと困る注意（前日の夜からの絶食）を目立たせませんでした。2回目の版で、今ある文言は変えずに提案にする、表は文字を縮めずに横に流す、見落とすと困る注意も目立たせる、を足しました。場面4は最初の版を書いたあとに作った場面ですが、2回目の直しには場面4の外しも使いました。直すのに使った場面で測っているので、表の数字は甘く出ている可能性があります。場面2は、2回目の版で 24/24 から 23/24 に1つ減りました（次の項目の 14px の回）。
- Skill ありで残った外しは、注意書きを 14px にした回です。Skill は注意書きの下限を 14px（デジタル庁の例外の線）にしていて、観点の線の 15px より低いので、Skill のとおりに動いて観点を外しています。Skill ありの回は、どれもブラウザで2つの幅を開いて撮ってから報告しました。
- Skill を置くだけにして、読むかどうかを AI に任せた条件も試しました（作者が使っているほかの Skill 32本と一緒に置いた状態）。場面1・2の4回はすべてこの Skill を読み、観点は場面1が 18/18、場面2が 14/16 でした。場面4は、最初の説明文では2回ともこの Skill を読まず（CSV を読む Skill だけを読んだ）、ブラウザでも開きませんでした。説明文に「CSV やデータから作る HTML のレポート」を足すと、3回ともこの Skill を読み、観点は 19/21 でした。場面3（文言だけ）の1回は読まずに、観点は全部満たしました。
- 1回の費用と時間（Skill なし → あり）は、場面1が 0.03 ドル・21〜23秒 → 0.11〜0.15 ドル・46〜60秒、場面2が 0.04 ドル・28〜29秒 → 0.10〜0.12 ドル・53〜66秒、場面4が 0.05〜0.06 ドル・32〜35秒 → 0.13〜0.14 ドル・57〜187秒でした。ブラウザで開いて撮って測る分が増えます。場面3は、Skill なしで 0.01 ドル・15秒、ありで 0.04 ドル・12〜13秒で、時間はほぼ変わりませんでした。
- 見た目の好み（色合い・余白の感じ）は測っていません。Skill なしの画面のほうが整って見える回もありました。測ったのは Chromium だけで、iPhone の Safari や Windows の Edge の実機では確かめていません。作業する AI が Sonnet 以外のとき、Claude Code 以外のツールで読み込まれるかは、確かめていません。

## 入れ方

```
npx skills add itoken-lab-jp/skills -g --skill web-ui-quality
```

`-g` は、プロジェクトごとではなく、自分のユーザーのどのプロジェクトでも使える場所に入れる指定です。手順の本文は [SKILL.md](../skills/web-ui-quality/SKILL.md) です。入れ方の詳しい説明（置かれる場所、ツールごとの違い）は [README](../README.md#入れ方) にあります。
