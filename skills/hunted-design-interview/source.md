# design-interview

大きめの新機能や作り直しを AI エージェントに「いい感じに作って」と頼むと、エージェントは、目的や範囲を推測で埋めて作り始めるか、長い仕様書や設計書を書いて「読んで承認してください」と返します。前者は作ったあとで「そうじゃない」になり、後者は読む量が判断できる量を超えて、読まずに承認することになります。

design-interview は、作り始める前に、決めることを一覧にして、エージェントが人に問いを回ごとに聞いて決め、決めたことを記録してから作る手順です。判断は会話の中で人が下し、文書はその記録にとどめます。記録は一緒に決めたものなので、書き上げた全文を改めて読ませて承認を求めることはせず、最後に「この記録で作り始めてよいか」を1問だけ聞きます。

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。

入れておくと、エージェントは次の場面で読み込みます。

- 新しいアプリ・機能・仕組みを「作りたい」「一緒に設計しよう」と頼まれたとき。
- データの持ち方や境界を変える作り直しを頼まれたとき。
- 実装の途中で、設計の前提が崩れたとき。

小さい直しや、数ファイルで済む道具には使いません。頼みに目的・範囲・完了の形が全部書いてあれば、聞かずに作ります。確実に読ませたいときは「design-interview の Skill に従って、作る前に決めよう」と名前で頼んでください。

## Skill を入れずに頼むと

「経費精算の CSV を会計ソフトに取り込める形にする道具を、いい感じに作って」という頼みで試しました（場面の詳細は下の「試した結果」）。Skill を入れない AI は、同じ場面を3回試して、リポジトリを先に読み、同じ月を2回取り込むと二重に登録される危険と、コマンドを打てない人に合った渡し方は押さえました。一方で、次のように外しました。

- 目的と成功の基準（何分で済めば成功か）を、3回とも聞きませんでした。
- 問いを番号つきでまとめはしても、推奨の無い開いた問いが混じり、「はい」で受け入れられる形にした回はありませんでした。言語や構成のような細部を「既定で決めた」と見せた回もありませんでした。
- 決めたことを記録に残し、「この記録で作り始めてよいか」を聞いてから作り始めた回はありませんでした。相手が「分からない」と答えた勘定科目の対応を、推測で埋めて進めた回が2回ありました。

## SKILL.md に書いてあること

AI が読むファイルです。どう動くかを確かめたいときは [SKILL.md](../skills/design-interview/SKILL.md) を開いてください。

- いつ使うか：大きめの新規と作り直し。頼みが「いい感じに」でも、作る前にここから入ります。人が「決めて進めて」と言ったら、目的・範囲と、後で変えにくい決定だけを1回で聞き、ほかは決めて記録します。
- 観点の一覧：目的、範囲、制約、使う人と使い方、データ、外とのつなぎ、守り、運用、受け入れの条件、進め方（作り直しなら、今の挙動のうち何を保つか）。資料で分かる事実は先に調べて埋め、人には聞きません。
- 聞き方：今答えられる問いを1回にまとめ、番号・選択肢・推奨・理由を添えて「はい」で推奨を受け入れられる形にします。答えに左右される問いは次の回に回します。最初の回には、資料から読めても目的と成功の基準、使う人を確かめる問いを入れます。人に聞くのは「何を・なぜ」と後で変えにくい決定で、やり方の細部は聞かずに決めて「決めた（既定）」として一覧に載せます。範囲から外すものも範囲の決定なので、黙って外さずに問いにします。一般論の答え（「拡張しやすく」「よくある形で」）は、使う場面1つで聞き返します。
- 記録と実装：決めたこと・理由・捨てた案・保留・範囲外・受け入れの条件を回ごとに足し、最後に「この記録で作り始めてよいか」を1問として聞いてから作ります。
- 設計へ戻るとき：決めた前提が事実と違った、受け入れの条件を満たすには範囲や境界を変えるしかない、小さいと見て始めた作業が大きくなった、のどれかなら、止まって決め直します。

## 試した結果

2026年11月に、架空の場面1つで試しました。作業する AI（Claude の Sonnet）と、頼んだ人とまわりの環境の役を、別々の AI（どちらも Sonnet）にしてやり取りさせました。作業する AI は実際のリポジトリを触らず、「【操作】cat README.md」のように書くと、相手役の AI が、場面ごとに決めた事実に沿って結果を返します。会話の記録を、Skill の有無を伏せて別の AI（Claude の Opus）が採点しました。守ってほしいこと（観点）を6個決め、それぞれを満たしたかを見ました。

場面：情報システムの担当から「経費精算の CSV を会計ソフトに取り込める形にする道具を、いい感じに作って」と頼まれます。リポジトリには作りかけの変換と、会計ソフトの取り込みの形の写し（「同じ内容を2回取り込むと二重に登録される」）があります。担当は、目的（経理の転記が月2時間かかる）や使う人（コマンドを打てない）を、聞かれたら答えます。どの会計ソフトに対応するかを聞かれると、最初は「いろんな会計ソフトに汎用的に」と答え、具体の場面で聞き返されると「本当は今の1つだけでいい」と本音を言います。

表の数字は、満たした観点の数を3回分足したものです。各行の分母は3回、計の分母は観点の数6×3回です。採点は観点ごとに「満たした・一部だけ・満たさない」の3段で、表は「満たした」だけを数えています。観点は Skill の書き手が決めたもので、重みは同じに置いています。Skill ありは、最初の版で測って外れた所（目的を聞かない、範囲外を黙って決める）を2回直し、3つ目の版（公開している版）で測った数です。

| 観点 | Skill なし | Skill あり |
|---|---|---|
| リポジトリを読んでから聞き、読めば分かることを聞かない | 3/3 | 2/3 |
| 今答えられる問いを番号・推奨・理由つきで1回にまとめる | 0/3 | 1/3 |
| 目的・範囲・使う人は聞き、細部は既定で決めて見せる | 0/3 | 3/3 |
| 一般論の答えを具体の場面で聞き返す | 1/3 | 2/3 |
| 後で変えにくい決定（二重取り込み、取り込みの方式）を問いにし、困る場面を添える | 1/3 | 2/3 |
| 決めたことを記録し、「この記録で作り始めてよいか」で入る | 0/3 | 2/3 |
| 計 | 5/18 | 12/18 |

- 版ごとの計は、最初の版が 8/18、1回直した版が 10/18、2回直した版が 12/18 でした。
- 往復（作業する AI と相手役が1回ずつ書く組）の数は、Skill なしが 5〜6、Skill ありが 6〜8 でした。増えた往復は、目的・使う人・範囲を聞いて決める分です。
- この場面のリポジトリには、対応する会計ソフトの名前が書いてありました。そのため、対応する範囲を聞かずに「その1つだけ」と置いた回があり、その回は一般論の聞き返しの観点を満たさないと数えています。この観点は、場面の作りのせいで十分には試せていません。
- 番号・推奨・理由つきでまとめる観点は、Skill ありでも「一部だけ」が多く残りました。推奨の無い問いや、相手が今は答えられない事実を尋ねる問いが混じったためです。リポジトリを読んでから聞く観点は、Skill ありの1回が、手元のサンプルを自分で集計する前に相手に中身を求めたため、一部だけになりました。
- 1つの場面の3回ずつで、数は少ないです。直すたびに同じ場面で測ったので、この場面に合わせて直しすぎている恐れがあります。
