# japanese-writing

AI が書く日本語は、箇条書きと「**見出し**：説明」の形が多く、文と文をつなぐ接続詞が少なく、話し言葉と書き言葉が混ざります。japanese-writing は、読み手と場面（社内か社外か、メールかチャットか）から文体・順番・長さを決める手順と、こうした形を避ける書き方をエージェントに渡します。

入れる前と後で、変更の記録から作業報告を書かせた例です。

```
入れる前：
- **ブラウザ操作（#104、11/9）**：Web ページを開く・読む・入力する作業の手順。手段の選び方と、ログインや取り消せない操作の扱いを決めた。

入れた後：
11月9日に、Web ブラウザを操作する手順を追加しました。ページを開く手段を選ぶ順序と、ログインや取り消せない操作の扱いを定めています。
```

## Skill あり・なしで比べる

同じ依頼を、同じモデル（Claude Sonnet）に、Skill を読ませる場合と読ませない場合で1回ずつ書かせました（2026年11月14日）。書き手は、会話の経緯や指示ファイルを持たない新しいサブエージェントです。Skill ありでは、書く前に SKILL.md と、Skill に含まれる業務の文書の資料（references/business.md）を読ませました。依頼は次の3つです。

| 依頼 | Skill ありで変わった所 |

| 変更の記録から、チーム向けの週報を Slack に書く | 冒頭に今週の結論を2文で置いた。日付に曜日を添えた。相談したいことを、来週の予定の文の中で目的とともに書いた。一方で、「調査中」の区分が消え、調査だけの件が完了の件と同じ並びに入った（悪くなった点） |
| 取引先に、納品日を延ばしたいとメールで頼む | 件名に用件と結論（12月5日に延ばしたい）を入れた。日付に曜日を添えた（暦で確かめると正しかった）。試用版を先に渡す理由（意見を反映できる）を足した |
| 公開する CLI の README の冒頭を書く | 「安心して試せます」「ダウンロードしてすぐ使えます」のような売り込みの言い方が消えた。金額の列を数字にすると何ができるか（数値として読み込める）を書いた |

同梱の検査スクリプトの指摘の数は、どちらも0〜1件で差が出ませんでした。この程度の長さの文なら、今のモデルは Skill が無くても、検査で拾える形（くだけた言葉、長すぎる文など）をあまり書きません。Skill の有無で、何をどの順で書くかが変わりました。

この3つの依頼では Skill によって結論や件名が先に来て、日付に曜日が付き、売り込みの言葉が消えました。1回ずつの比べなので、同じ差がいつも出るとは限りません。週報の依頼は、SKILL.md の中の例（変更の記録から書く作業報告）と似ています。README の依頼では、Skill なしの文だけが「「1,200円」は 1200 になります」という具体例を書いていて、その点は Skill ありの文より分かりやすくなっていました。

## 決まりを言葉どおりに当てる弱みを直した（2026年11月15日）

前の版（2026年11月14日の版）には、SKILL.md の「文章の形」の決まりを、理由が当たらない場面にも言葉どおりに当てる弱みがありました。倉庫のお知らせを直させる題材では、「理由は1文にまとめる」を安全の注意にも当て、「濡れた手で触らないでください。感電のおそれがあります。」を「感電のおそれがあるため、濡れた手で触らないでください。」に直しました（6回のうち5回）。禁止が文の後ろに回り、通りがかりに読む人には「触らない」が届きにくくなります。休憩室の貼り紙を書かせる題材では、「説明は段落の文章で書く」を貼り紙にも当て、経緯の段落から書き始めました。

この版では次を変えました。

- エージェントは最初に、書くものがどう読まれるかを決めます（通読する、探して拾い読みする、通りがかりに数秒で見る、会話の流れで読む）。数秒で見るものは、してほしい行動を最初に短く並べます。
- 「文章の形」の9つの決まりに、読み手のどの問いに答えるための決まりかを付け、言葉に当たっても読み手が困らない箇所は変更しない、と書きました。
- 理由の置き場所、接続詞、主題（「〜は」）の決まりを、日本語の文法の説明に合わせて書き直しました。理由を後ろの文に置く形は、結論が既に文脈にある場合と、禁止や指示を先に伝える場合の形です。接続詞は、前後の関係を読み手が補えない箇所に置き、同じ主題が続く文には置きません。主題は次の文にもかかるため、同じ主題が続く間は「〜は」を毎文に書きません（庭三郎「[現代日本語文法概説](https://niwasaburoo.amebaownd.com/)」の 50・60・61 章）。
- 題名・見出し・最初の文の強さを本文に合わせること、材料に無いことを足さないことを足しました。
- 検査スクリプトの細かい使い方は references/check.md に移しました。
- 本文を長さの上限に収めるため、次を削りました。伝わり方の4つ（正確さ・分かりやすさ・ふさわしさ・敬意と親しさ）のどれを優先するかを場面ごとに決める、という文。「前の文は『これは』『その結果』で受ける」「短い文が3つ続く場合は1文にまとめる」。話し言葉の言い換えの例のうち3つ（見るところ→確認箇所、わざと→意図的に、次は→以下は）。「補足の情報は『〜こともできます』と書く」。

作業する AI（Claude Sonnet）に、題材のファイルが入ったフォルダーで書かせ、Skill の有無を伏せて別の AI（Claude Opus）に採点させました。題材ごとに決めた観点（守ってほしいこと）について、満たした（2点）、一部（1点）、満たさない（0点）で数え、流した回数の分を足しました。回数は括弧の中に書きます。

| 題材 | Skill なし | 前の版 | この版 |

| 記事・障害のお知らせ・上司への提案を書く（3題材の合計） | 103/144（各3回） | 214/288（各6回） | 234/288（各6回） |
| 不自然な形が9つある報告を直す | 50/60（3回） | 56/60（3回） | 55/60（3回） |

- 倉庫のお知らせの題材は、前の版が Skill なしより低く出ました。安全の注意を崩した回は、前の版で6回のうち5回、この版で6回のうち2回です（Skill なしは3回のうち1回）。減りましたが、無くなってはいません。
- 貼り紙の題材は、前の版が Skill なしより低く、この版で上回りました。ただし、この題材は弱みを見つけるのに使ったもので、結果を見ながら Skill を直しています。この版の1つ前の下書きは、6回で 69/84 でした。
- 書く題材3つの差は 288 点のうち 20 点です。書いている途中、同じ中身で文の位置を変えただけの下書きが、3回ずつで 107〜115/144 と動きました。3回ずつの差は当てにできないと分かったので、この3題材は6回ずつ流しました。不自然な形を直す題材と、エラー画面とヘルプを書く題材は3回ずつのままで、56 と 55、40 と 42 の差はこの幅の中です。
- AI が書いた文章で、文法の教科書にある誤り（同じ主題を毎文書く、「それ」「それら」で受ける、受けるものの無い「のです」、「することができる」）を数えましたが、Skill のあるなしにかかわらず、ほぼ出ていませんでした。このため、文法からは新しい決まりを足していません。文法の説明は、すでにある決まり（理由の置き場所、接続詞、主題）が、どんな場合の決まりかを書き直すのに使いました。
- 題材を作った人と Skill を書いた人が同じで、作業したのは Claude Sonnet のみです。

## 使い方

日本語の文章を書く依頼をすると、エージェントが Skill の説明を見て自動で読み込みます。読み込まれない場合は、依頼に「japanese-writing の Skill を使って」と書きます。

同梱の検査スクリプト `scripts/check.mjs` は、書いた文章のファイルを読み、確認したほうがよい箇所を行番号付きで一覧にします。ファイルは書き換えません。エージェントは Skill の手順に従って実行します。自分で実行する場合は次のとおりです。

```
node skills/japanese-writing/scripts/check.mjs 文章.md
```
