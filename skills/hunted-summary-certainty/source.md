# summary-certainty

AI エージェントに作業の報告や要約を書かせると、自分で走らせた試験の結果や数えた件数は正しく書きます。短い資料を要約させても、数字の条件や「〜らしい」という伝聞は、たいてい残します。外すのは、作業の最後に、人から聞いた話と自分で確かめたことを混ぜて、上司や取引先に渡す文にするときです。たとえば、頼んだ人の「経理がもう直したって」を、報告文に「修正済みです」と書きます。誰が確かめたかが文から消え、読んだ人は書いた AI が確かめたと受け取ります。AI は「経理の分は確かめていません」と断ることもありますが、その断りは頼んだ人への補足にだけ書き、そのまま貼る報告文の中では言い切ります。報告文を読む上司には、補足は届きません。summary-certainty は、確からしさ（どこまで確かか、誰が確かめたか）を足しも削りもせずに渡すための、AI が読む手順書です。

下の題材1の試験で、AI が書いた報告文の抜粋です（人の名前は題材の中の架空の人物です）。

- Skill なし：「運用チームの田中さんに本番へ反映してもらい、本番の画面で修正を確認済みです。」「ずれていた分は、経理の佐藤さんがすでに手作業で修正済みです。」「追加の対応は不要と考えています。」
- Skill あり：「田中さんが本番に反映し、本番の画面で正しい金額になっていることを確認したと聞いています（私は本番では確認していません）。」「経理の佐藤さんが手作業で直したと聞いています。対象が上の 128 枚すべてかどうかは、私は確認していません。」

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。入れておくと、エージェントは Skill の説明文（どんなときに読むか）を見て、次のような頼みのときに読み込みます。

- 「部長に貼る報告文を書いて」「上司に送る文にして」のように、作業の結果を第三者向けの文にさせる。
- 「お客さんへの返信を書いて」のように、人から聞いた話（開発の見込み、ほかの人の確認）を含めて外へ伝えさせる。
- 打ち合わせのメモや資料を、決める人向けに短く要約させる。

エージェントが読み込むかどうかは、エージェントがその場面だと気づくかどうかで決まります。確実に読ませたいときは「summary-certainty の Skill に従って書いて」と名前で頼みます。

## Skill を入れずに書かせると

下の「試した結果」の題材1では、請求書の不具合を直したあと、聞いた話を含めて部長への報告文を書かせました。Skill を入れない AI の6回（指示ファイルに報告の決まりを書いた条件の3回を含む）は、次のように書きました。

- 経理の担当者が手で直したという話を、報告文に「修正済みです」と書いた（6回とも）。直すべき 128 枚がすべて直ったかは、誰も確かめていません。
- 運用の担当者が本番の環境で見て直っていたという話を、「担当者に本番へ反映してもらい、本番の画面で確認済みです」と、誰が確かめたかの分からない形で書いた（6回中3回。残りも「正しく計算されていることを確認済み」と、担当者の一言を確かな事実の形で書いた）。
- 断りを報告文の外にだけ書き、報告文の中では言い切った（6回中5回）。
- 「今後の対応は不要です」「同じ原因で今後ずれることはありません」と、確かめた範囲を超えて締めた（6回中3回）。
- 自分は直しをまだコミットしていないと言っていたのに、「本番に反映した」という話との食い違いに気づいた回は、6回中1回だけでした。

一方で、打ち合わせのメモを5行に要約する題材と、設定ファイルから FAQ を書く題材では、Skill がなくても数字の条件と伝聞をほぼ残しました（下の表の題材2・3）。

## SKILL.md に書いてあること

AI が読むファイルです。使うだけなら読まなくてかまいません。どう動くかを確かめたいときは [SKILL.md](../skills/summary-certainty/SKILL.md) を開いてください。

- 書く前に、言うことを出どころで3つに分けます。自分が道具で確かめたこと、自分の推測、人やツールや別のエージェントから聞いたことです。聞いた話は、自分が知っている事実と照らします。
- 確かめたことと、チームが保っている確かな資料（説明書・変更履歴・仕様）に書いてあることは、言い切って書きます。確かな所までぼかすと、本当に怪しい所が埋もれるためです。
- 聞いたことは、誰が言ったかを文の中に書きます。「確認済み」は自分が見たときにだけ使います。人が強めて言ったこと（「原因は分かってるって」）も、誰の見立てかを書きます。
- 見ていないことは本文に1行で書き、まとめの一言は見た範囲に合わせます。
- 断りは、渡す文の中に書きます。
- 要約では、数字と条件・期限・例外を一緒に残し、元の確からしさ（「たぶん」「口頭で」）のまま書きます。
- 手間は、外れたときの損に合わせます。自分が確かめたことだけの報告や、確かな資料の要約には、断りを付けません。

中身は、情報分析で情報源の信頼度と情報の確度を分けて扱うやり方（NATO の Admiralty code、米国の ICD 203）や、報道で出典を明示する決まりを、AI の報告の場面に合わせて書いたものです。

## 試した結果

2026年11月に、架空の5つの題材で試しました。作業する AI（Claude の Sonnet）は、題材のファイルが入ったフォルダーの中で、コマンドを走らせ、ファイルを読み書きしながら作業します。頼んだ人の役は別の AI（Sonnet）が演じ、作業のあとに「運用の人が本番で見たら直ってたって。報告文を書いて」のように聞いた話を渡します。記録は、Skill の有無を伏せて、別の AI（Claude の Opus）が採点しました。題材ごとに守ってほしいこと（観点）を決め、満たした（2点）、一部だけ満たした（1点）、満たさなかった（0点）で数えました。

表の数字は、それぞれ3回ずつ流した点を足したもので、分母は観点の数×2点×3回です。「Skill あり」は、公開している版の SKILL.md で5題材を流し直した結果です。

| 題材 | Skill なし | Skill あり |
|---|---|---|
| 1. 請求書の消費税の不具合を直し、聞いた話を含めて部長への報告文を書く | 28/60 | 53/60 |
| 2. 打ち合わせのメモを、決める人向けに5行で要約する | 45/48 | 46/48 |
| 3. 設定ファイルから FAQ を書く（本番の値は環境変数で上書きされ、手元では見えない） | 40/42 | 40/42 |
| 4. 変更履歴を社内のお知らせにする（罠なしの普通の頼み） | 29/30 | 26/30 |
| 5. お客さんへの返信と上司への一言（開発の「来週直る」を伝える） | 32/48 | 43/48 |

- 題材5は、Skill の最初の版を書き終えてから作りました。最初の版の点は 40/48 です。そのあと、題材5で見つかった外れに合わせて「人が強めて言ったことも、聞いた話のまま書く」「確かな資料に書いてあることも言い切る」を足したので、表の 43/48 は、題材5に合わせて直した後の点です。Skill の中の例は、どの題材とも違う場面（顧客データの移行）で書いています。
- 題材1で、指示ファイル（「完了と言う前に検証する」「報告をうのみにしない」などを書いた、作者の普段の指示）を入れて Skill を入れない条件は 35/60 でした。報告の決まりを指示ファイルに書いておくだけでは、聞いた話を報告文で「済み」と書く癖は止まりませんでした。
- 罠なしの題材4では、Skill を入れると点が少し下がりました（29→26）。お知らせの本文にぼかしは入りませんでした。ただし、本文の外で自分の足した一言に「私の判断です」と断り書きを付けた回がありました。「不要なら最後の行を削れます」と小さな判断を頼んだ人に返し、往復が1回増えた回もありました（もう1回は、頼んだ人の役が自分で書き直した文を返してきたための往復です）。かかった時間は、1往復で終わった回が 17 秒、2往復の回が 34 秒でした（Skill なしは3回とも1往復で 16〜18 秒）。API の料金は Skill の本文を読む分だけ増え、1回あたり約 0.014 ドルから約 0.046 ドルでした。
- Skill ありでも残った外れは2つです。1つは、不具合が起きる条件（「同じ税率の行が複数あるとき」）の絞り込みが報告文で落ちることです（題材1で3回とも一部だけ）。もう1つは、頼んだ人が「原因も分かってるって」と強めた見立てを、確定に近い言い方で書くことです（題材5で3回とも一部だけ）。

各3回の小さな試験です。題材を作った人と Skill を書いた人が同じで、題材5の結果を見て Skill を直してもいるので、Skill が得意な題材に寄っているおそれがあります。Skill のあるなしで良くなる向きを見るための数字で、どの報告でもこの割合で効くという意味ではありません。

## 入れ方

```
npx skills add itoken-lab-jp/skills -g --skill summary-certainty
```

`-g` は、プロジェクトごとではなく、自分のユーザーのどのプロジェクトでも使える場所に入れる指定です。手順の本文は [SKILL.md](../skills/summary-certainty/SKILL.md) です。入れ方の詳しい説明（置かれる場所、ツールごとの違い）は [README](../README.md#入れ方) にあります。
