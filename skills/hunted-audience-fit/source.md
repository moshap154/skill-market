# audience-fit

AI に「新しく入るアルバイトの人が初日に一人で開店準備ができるように、店長の話のメモを1枚にまとめて」と頼むと、中身は正しいのに、55〜70行の「1枚」が返ってきます。月初や棚卸しの日だけの作業も並び、メモにあった「ドロア」（レジの引き出しのこと）という言葉は、初日の人には通じないのに、説明なしでそのまま書かれます。架空の場面で Skill を入れない AI に試させると、資料の中に書いてある条件はほとんど見落とさず、外したのは、作った物を渡した先のことでした（下の「Skill を入れずに頼むと」）。読む人の持ち時間、読む人が知っている言葉、読んだ相手がどう動くかは、資料に書いていないからです。

audience-fit は、AI が作った物（返事・報告・メール・お知らせ・手順書・質問のリスト）を渡す前に、受け取る人の側から一度確かめるための、AI が読む手順書（Skill）です。Skill は、エージェントが作業に合わせて読み込む手順書のファイルです。中身は4つの確かめで、頼みと並べて頼まれていない物を削る、元の資料から写した言葉を読む人が知っているかで分ける、社外に出す文を相手の席で読む、自分が書いた方針を中身が守っているかを照らす、です。

向いているのは、AI に、頼んだ自分とは別の人が読む物を作らせている人と、AI の返事が長いと感じている人です。文体・敬語・文章の組み立てを整える Skill ではありません。公開する記事や README を、事情を知らない別の読み手に読ませて確かめる手順でもありません（この Skill は、書いた AI 自身が渡す前にする、軽い確かめです）。

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。入れておくと、エージェントは Skill の説明文（どんなときに読むか）を見て、次のような頼みで読み込みます。

- 「新しく入るアルバイトの人向けに、手順を1枚にまとめて」
- 「明日の朝、社長に1分だけ口頭で報告する。話すメモを作って」
- 「障害の社内メモから、取引先に送るお知らせのメールを書いて」
- 「外注先に、納期の前倒しを頼むメールを書いて」

確実に読ませたいときは「audience-fit の Skill に従って」と名前で頼みます。下の「試した結果」のとおり、頼みに、読む人（「新人向けに」）や枠（「1枚で」「1分で」のような量や時間の限り）の言葉が無いと、置いておくだけでは読まれないことがあります。

## Skill を入れずに頼むと

架空の場面で、Skill を入れない AI に同じ頼みを3回ずつさせました（場面の中身と数え方は、下の「試した結果」）。

- 「新機能の需要を確かめるインタビューの質問のリストを作って」と頼むと、3回とも、30分のインタビューに21〜23問を並べました。3回とも冒頭に「『あったら使いますか』のような仮定の質問は当てにならない」と自分で書いたうえで、「いくらなら払いますか」を断りなく入れ、その答えを開発を決める目安にも使いました。自分で当てにならないと書いた種類の質問です。頼みにあった「払うか確かめたい」という言葉を、そのまま相手への質問にしたために混ざりました。
- 「外注先に納期の前倒しを頼むメールを書いて」と頼むと、3回中2回、「頼れるのは貴社だけ」のように、ほかに頼める先が無いことを丁寧さのつもりで書きました（相手に知られると、費用や条件の話で頼む側が不利になります）。分けて納めてもらう案や追加費用の出し方は、3回ともできていました。
- 「新人向けに開店準備を1枚に」と頼むと、3回とも55〜70行になり、まれな日の作業が残り、「ドロア」と、レジの画面のボタンの名前「開設」は、言い換えも説明もありませんでした。
- 「社長に1分で口頭で報告するメモ」では、3回とも1分で話せる量（書き手が置いた目安で350字）を超え、関係の薄い話や、社長には通じにくい現場の言葉が残る回が1回ありました。
- 返事の長さの観点は、どの場面でも3回そろっては満たせませんでした。頼まれた成果物の外に、構成の説明、削った物の一覧、代わりの案が付きます。

同じ AI に、別の人が取ったインタビューの記録を読ませると、「使うと思います」という答えを証拠にしないことは3回ともできました。原則は知っていて、自分が作る側に回ると当てはめない、という外し方です。

## SKILL.md に書いてあること

AI が読むファイルです。使うだけなら読まなくてかまいません。下は中身の要約で、全文は [SKILL.md](../skills/audience-fit/SKILL.md) にあります。

- 書き終えてから一度だけ確かめます。作っているあいだに足す項目は一つひとつ正しく見えるので、書きながらでは止まらないためです。確かめたこと自体は返事に書きません。
- 頼みの文と作った物を並べ、頼まれた物そのものか、無いと相手が次に動けない物だけを残します。大きさの目安を数字で置いています（数字や事実を聞かれたら3文まで、判断や案なら結論1文と理由3つまで、成果物の外の説明は3文まで、時間や紙の枠がある物は1項目にかかる分数や行数で割って入る数まで）。削った物を「補足」として付け直しません。
- 削らない物も決めています。危ないこと、相手が決めないと進まないこと、「詳しく」「省かずに」と頼まれた物、記録・監査・引き継ぎのように後から事実をたどる物です。
- 元の資料から写した言葉（専門語・社内の呼び名・略語）を拾い、読む人がその言葉に前に出会っているかで、言い換える・その場で一言添えて使う・そのまま使う、に分けます。
- 社外や別の部署の相手に出す文は、相手になって読みます。頼んだ人の立場を弱くする事実や内輪の事情を書いていないか、社内で決まっていないことを相手が当てにする形で書いていないかを見ます。相手に起きたことは隠さずに書きます。
- 「〜は聞かない」のように自分で方針を書いたら、中身がそれを守っているかを上から読んで照らし、反する物は、但し書きを付けて残すのではなく、外します。
- 書いた本人が自分で確かめられる範囲には限りがあります。多くの人に公開する文章や、読み違いの損が大きい文書は、この確かめで済ませず、事情を知らない別の読み手に読ませるよう、AI に書いています（読ませる手順そのものは、この Skill には入っていません）。

## 参考にしたもの

言葉の分け方（言い換える・説明を添えて使う・そのまま使う）は、次の2つの考え方を借りています。分け方の見出しは原文で確かめました。

- 国立国語研究所「病院の言葉」委員会「[『病院の言葉』を分かりやすくする提案](https://www2.ninjal.ac.jp/byoin/)」：患者に通じにくい言葉を、日常語で言い換える・明確に説明する・重要で新しい概念の普及を図る、に分けています。
- 文化審議会「[公用文作成の考え方（建議）](https://www.bunka.go.jp/seisaku/bunkashingikai/kokugo/hokoku/pdf/93731901_01.pdf)」（2022年、PDF）：専門用語を、言い換える・説明を付けて使う・普及を図るべき用語は工夫してそのまま用いる、に分けています。

## 試した結果

2026年11月に、架空の場面で試しました。作業する AI（Claude の Sonnet）は、資料の入ったフォルダーの中で作業します。記録は、Skill の有無を伏せて、別の AI（Claude の Opus）が採点しました。場面ごとに守ってほしいこと（観点）を決め、それぞれを満たしたかを見ました。

- 場面1：月次レポートの作業を楽にする改善案を出す。観点は7個（最後の1つが、絞って短いこと）。
- 場面2：需要を確かめるインタビューの質問のリストを作る。観点は7個。
- 場面3：外注先に納期の前倒しを頼むメールを書く。観点は7個。
- 場面4：新人のアルバイト向けに、開店準備を1枚にまとめる。観点は7個。
- 場面5：社内の障害メモから、取引先41社に送るお知らせを書く。観点は6個。
- 場面6：社長に1分で口頭で報告するメモを作る。観点は7個。
- 場面7：2つのサービスのどちらがよいかを「一言で」答える。観点は5個。
- 場面8：内部監査に出す報告を、時系列で省かずにまとめる。詳しさが要る頼みで、Skill が削りすぎないかを見る。観点は7個。
- 場面9：見積もりのお礼と返事の期日を伝える返信を書く。落とし穴の無い場面で、Skill を入れたせいで重くなっていないかを見る。観点は4個。

表の数字は、満たした観点の数を3回分足したものです。分母は観点の数×3回です。採点は観点ごとに「満たした・一部だけ・満たさない」の3段で、表は「満たした」だけを数えています。

| 場面 | Skill なし | この Skill を読ませる |
|---|---|---|
| 1 業務の改善案 | 16/21 | 20/21 |
| 2 インタビューの質問 | 12/21 | 21/21 |
| 3 納期の前倒しを頼むメール | 13/21 | 19/21 |
| 4 新人向けの1枚 | 9/21 | 16/21 |
| 5 取引先へのお知らせ | 12/18 | 12/18 |
| 6 社長に1分の報告 | 13/21 | 18/21 |
| 7 どちらがよいか一言で | 14/15 | 13/15 |
| 8 監査向けに省かずに（詳しさが要る） | 14/21 | 19/21 |
| 9 お礼の返信（落とし穴なし） | 9/12 | 12/12 |
| 計 | 112/171 | 150/171 |

- 右の列は、Skill の本文を必ず読ませた条件です。場面1〜4は、Skill なしの外し方を見てからこの Skill を書いたので、数字は甘く出ています。場面5〜9は、Skill を書いたあとに初めて試した場面です。場面も観点も字数の目安も、この Skill の書き手が決めたもので、Skill の中の大きさの目安と同じ人が決めています。長さの観点は Skill に有利です。
- 場面5は差が出ませんでした。Skill なしでも、社内の呼び名や担当者の名前は3回とも外に出しませんでした。再発防止をいつ知らせるかを書かないこと、本文が目安の500字を少し超えることは、Skill ありでも残りました。場面7も差は無く、Skill なしで足りていました。
- 場面4では、Skill ありでも、画面のボタンの名前「開設」に説明が付かない回が3回中2回、採点の観点で置いた目安の35行を超える回が1回（45行）ありました。SKILL.md の例が「開設」を説明なしで書いていたためで、例を説明を添える形に直して測り直すと、3回とも「画面の『開設』」のように場所が添えられました（この版は 17/21。表は直す前の数字のまま）。
- 場面8（詳しさが要る頼み）で、Skill が日時・件数・金額・人を削ることはありませんでした。点が上がった分は、文書の外に添える説明が短くなったことによります。
- 場面1・5・7は、言い回しを直す前の版で測りました（直したのは、経緯を知らない読み手に読ませて止まった所の説明と、方針を照らす段の例）。ほかの6場面は、直したあとの版です。
- Skill を置くだけにして、読むかどうかを AI に任せた条件も試しました（作者が使っているほかの Skill 38本と一緒に置いた状態、言い回しを直す前の版）。場面3・4・5・6は3回ともこの Skill を読みました。場面2は3回中1回、場面1は0回でした。頼みに「〜向けに」「1分で」「取引先に送る」のような、読む人や枠の言葉が無い場面です。場面7・8・9（一言の答え、詳しさが要る頼み、落とし穴なし）は読まず、それで足りていました。9場面の合計は、ほかの38本だけを置いたときが 111/171、この Skill も置いたときが 134/171 でした（上の表の「Skill なし」112/171 は、Skill を1本も置かない別の回です）。
- 1回の費用は、Skill なしで 0.01〜0.07 ドル、ありで 0.01〜0.07 ドルで、ほぼ変わりません。返事の字数は、9場面のうち8場面で減りました（たとえば場面1は約1,560字から約810字、場面4は約670字から約170字）。場面7はどちらも110字前後です。
- 場面ごとに3回ずつで、数は少ないです。受け取る人が実際に読んで使えたかは確かめていません（採点は AI です）。試したのは Claude Code と Sonnet の組み合わせだけです。Skill の形式は共通なので Codex などでも置けますが、ほかのモデルやツールで同じように読まれ、同じように効くかは、確かめていません。

## 入れ方

```
npx skills add itoken-lab-jp/skills -g --skill audience-fit
```

`-g` は、プロジェクトごとではなく、自分のユーザーのどのプロジェクトでも使える場所に入れる指定です。手順の本文は [SKILL.md](../skills/audience-fit/SKILL.md) です。入れ方の詳しい説明（置かれる場所、ツールごとの違い）は [README](../README.md#入れ方) にあります。
