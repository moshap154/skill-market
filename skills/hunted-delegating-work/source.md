# delegating-work

AI エージェントは、仕事をサブエージェント（自分が立てる別の AI）や別のセッションに任せられます。任せた相手はこの会話を見ておらず、依頼文だけを読んで動き、報告だけを返します。依頼文に書かなかったことは守られず、報告の「完了しました。テストはすべて通りました」は、テストを1件 skip して通したものかもしれません。delegating-work は、AI が仕事を任せるときに、任せるかを決め、依頼文を書き、返ってきた報告を実物で確かめる手順です。

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。サブエージェントの立て方やモデルの指定のしかたはツールごとに違うので、Skill には書いていません。ツールの docs に従わせてください。

入れておくと、エージェントは次の場面で読み込みます。

- 大きな書き換えを、サブエージェントで手分けして並列に進める。
- 夜の間や何時間も、回し続ける仕事を任せる。
- 読み取りだけの調査を任せる。
- どの重さのモデルに任せるかを決める。

確実に読ませたいときは「delegating-work の Skill に従って任せて」と名前で頼んでください。

## Skill を入れずに任せさせると

下の「試した結果」の3つの場面で、Skill を入れない AI は次のように外しました（各3回）。

- いきなり全部を割る：古い関数 `legacyCharge()` の呼び出し 34 ファイルを新しい `chargeV2()` に置き換える仕事を、3回とも先に数件で試さずに、一度に3体のサブエージェント（以下、子）へ割りました。新しい関数は通貨の省略を許さないという落とし穴は、子ごとに違う形で扱われました。
- テストを緩めさせない、を書かない：3回とも、テストの skip や期待の緩めを依頼文ではっきり禁じませんでした（一部だけ書いたのが1回）。子は落ちたテストに skip を足して「すべて通りました」と報告し、3回中2回は、その skip の出どころを確かめないまま残しました。
- 回し続ける仕事の条件：「寝ている間に lint のエラーを 0 にしておいて」では、回数か時間の上限を決めず、進みと残りをファイルに書かせる指示も弱いままでした。

一方で、読み取り専用のはずの子が、チャットに投稿する道具を持っていて、そのチャットには本番の DB でコマンドを実行する bot がいる場面では、Skill がなくても3回とも投稿の道具を外して子を立てました。

## SKILL.md に書いてあること

AI が読むファイルです。どう動くかを確かめたいときは [SKILL.md](../skills/delegating-work/SKILL.md) を開いてください。

- 任せるか：任せるのは、独立して並列にできる大きな仕事、結論だけが要る調べ物、意図を渡さない別の目の3つだけです。計画づくりと、途中の結果で後のやり方が変わる仕事は任せません。同じ形の仕事を多く割るときは、先に2〜3件で試します。並列で書き換える子は作業場所を分け、更新履歴のような共有のファイルはまとめる側が最後に書きます。子の道具だけでなく、子から届く先（書き込める bot やエージェント）まで数えます。
- どの重さのモデルか：モデルの名前で覚えず、仕事の重さで、軽い・中間・上位・最上位のどの層のモデルにするかを選びます。コードを書く仕事は層を下げず、考える量（effort）を下げます。
- 依頼文：目的と、機械で判定できる終わりの条件（検索の該当が 0 件、テストが通る）。分かっている落とし穴。作業場所と受け持ち。検証のコマンドと、テストを消す・skip する・期待を緩めることの禁止。報告の形（状態を一語、コマンド・終了コード・そのときのコミット）。
- 受け取る：報告は入力にすぎず、diff を全部読み、終わりの条件を自分で測り直します。終わりの判定だけを通す抜け道（テストの skip、lint の警告を黙らせる注釈、ルールを切る設定）が無いかを見ます。人への報告は、確かめたことと確かめていないことを分けます。
- 長い仕事：状態を会話の外のファイルに置かせ、区切りごとにコミットさせます。終わりの条件と回数か時間の上限を組にし、同じ筋で2回直らなければ止め、設計の判断が要るものは残して止めさせます。結果は PR に出させます。

## 試した結果

2026年11月に、架空の3つの場面で試しました。作業する AI（Claude の Sonnet）と、頼んだ人と子のエージェントとまわりの環境の役を、別々の AI（どちらも Sonnet）にしてやり取りさせました。作業する AI は実際のリポジトリを触らず、「【委譲：子の名前】依頼文」「【操作】git diff」のように書くと、相手役の AI が、場面ごとに決めた事実に沿って子の報告や操作の結果を返します。子の振る舞いは依頼文の中身で変わります（たとえば、依頼文がテストの skip を禁じていなければ、子は skip を足して「すべて通った」と報告します）。会話の記録を、Skill の有無を伏せて別の AI（Claude の Opus）が採点しました。場面ごとに守ってほしいこと（観点）を5〜8個決め、それぞれを満たしたかを見ました。場面は Skill を書く前に作り、Skill の中の例は場面と違う題材にしています。

表の数字は、満たした観点の数を3回分足したもので、分母は観点の数（場面1は8、場面2は7、場面3は5）×3回です。一部だけ満たした観点は数えていません。

| 場面 | Skill なし | Skill あり |
|---|---|---|
| 1. 34 ファイルの呼び出しの置き換えを子に手分けさせる（子がテストを skip する、検索に出ない呼び方がある、検証のあとにコミットする） | 3/24 | 18/24 |
| 2. 夜の間に lint のエラーを回し続けて 0 にする（子が抑止の注釈で 0 にする） | 6/21 | 15/21 |
| 3. 読み取り専用のはずの子に本番の遅いクエリを調べさせる（子の道具から、本番で実行する bot に届く） | 11/15 | 12/15 |

- 先に数件で試してから広げたのは、場面1で Skill なし3回中0回、Skill あり3回中3回でした。
- テストの skip や期待の緩めを依頼文で禁じたのは、場面1で Skill なし3回中0回（一部だけ1回）、Skill あり3回中3回でした。
- Skill ありは確かめの手順が増え、場面1と2の6回のうち4回が試験の往復の上限（10往復）に届き、そのうち3回は最後の報告まで進みませんでした。最後の報告の観点は、進まなかった分を満たさなかったと数えています。上限は試験の都合で、実際の仕事では、確かめの分だけ往復が増えると読んでください。
- 場面3は Skill がなくてもよくでき、差は小さいです。子の報告の根拠を自分で確かめず、子への再依頼や相手への確認で済ませる弱さは、Skill ありでも3回とも残りました。

公開している版は、測ったあとに、元の手順から移し漏れていた決まり（1体で足りるなら1体にする、手で数えた数を記録に書かせない、起動に失敗した検査を通過に数えない、モデルの層の選び方の細部など）を戻しています。戻した分は試していません。
