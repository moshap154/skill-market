# prototyping

AI に「この仕様の案、動かして確かめたいから試作を作って」「設定画面の案をいくつか見比べたい」と頼むと、試作そのものはよくできたものが返ってきます。架空の場面で Skill を入れない AI に試させると、外したのは、試作を渡したあとでした（下の「Skill を入れずに頼むと」）。試作を触った人が「こう決めた」と伝えても、仕様書の未決の欄を書き換えず、「頼まれていないので」と聞いて止まります。決まったことは会話の中にしか残らず、あとで実装する人には伝わりません。試作のファイルも、消すのか残すのかを決めないまま、作業中のフォルダーに置いて終わります。

prototyping は、決める前に動かして確かめるための捨てる試作（プロトタイプ）を、AI に作らせる・渡させる・片付けさせるときの、AI が読む手順書（Skill）です。Skill は、エージェントが作業に合わせて読み込む手順書のファイルです。試作の値打ちは、試作そのものでなく、それで決まったことにあります。この Skill は、決まったことを仕様書や票（Issue・チケット）に書き残す所と、試作の行き先を決める所を中心に書いています。

向いているのは、Claude Code や Codex に、仕様の案や画面の案を試作させてから決めている人です。試作を経ない本番の実装や、関数を1回動かして結果を知りたいだけのときには使いません。

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。入れておくと、エージェントは Skill の説明文（どんなときに読むか）を見て、次のような頼みで読み込みます。

- 「この仕様の案、紙の上だと良さそうだけど、動かしてみないと分からない。試作を作って」
- 「設定画面の通知の欄、どう見せるのがいいか、案をいくつか見比べたい」
- 「先週見た試作は B 案に決めた。本番にして」

確実に読ませたいときは「prototyping の Skill に従って」と名前で頼みます。

## Skill を入れずに頼むと

架空の場面で、Skill を入れない AI に同じ頼みを3回ずつさせました（場面の中身と数え方は、下の「試した結果」）。

- 「予約の状態の案を試作して」と頼むと、3回とも、ダブルクリックで開ける1つの HTML を作りました。業務の言葉のボタンがあり、時計を進められ、仕様書で未決だった2点（日程変更のあとのキャンセル料をどちらの利用日で数えるか、失効した仮予約を確定しようとしたらどうするか）を切り替えて比べられ、本番のコードには触っていません。ここは Skill が無くてもできていました。
- その試作を触った人が、決めた2点を伝えて「今日はここまで」と言うと、3回とも、仕様書の「まだ決めていないこと」を書き換えませんでした。「頼まれていないので手を付けていません」「やる場合は言ってください」と返し、決まったことは会話の中にしか残らず、来週実装する人は仕様書を読んでも分かりません。試作のファイルも、3回とも「コミットしていません」と伝えるだけで、消すのか残すのかを決めませんでした。
- 「設定画面の案を見比べたい」と頼むと、3回とも、構造の違う案を作りましたが、今の設定画面とは別のページに置きました。別のページでは、プロフィールなどほかの欄と並んだときの長さや詰まり方を見比べられません。1回は、案を切り替える仕組みが無く、縦に並べただけでした。
- 「B 案に決めた。本番にして」と頼むと、3回とも、試作が省いていた保存をつなぎ、落ちた案と切り替えのバーを消しました。一方で3回とも、試作の説明の文書（3案の見方を書いたメモ）を消しただけで、B に決めたことも理由も、文書にもコミットにも残しませんでした。あとで「なぜ B なのか」をたどれません。

## SKILL.md に書いてあること

AI が読むファイルです。使うだけなら読まなくてかまいません。下は中身の要約で、全文は [SKILL.md](../skills/prototyping/SKILL.md) にあります。

- この試作で何を決めたいのかを1〜2文で、試作の画面の上と、渡すときの返事に書きます。頼みや仕様から読み取れれば、聞かずに置きます。
- 本番のコード・データ・保存につながず、試験や、あとで広げるための設定・抽象を足さず、試作と分かる名前と置き場にします。開くのに要るのは、ファイルを開くか、コマンド1つまでです。
- 状態や流れを確かめる試作では、日付や時間を進める手段を付け、決まっていない点は両方の決め方を画面で切り替えられるようにします。
- 見た目を見比べる試作では、形の違う案を3つ前後、今の画面の中のその欄の場所に出し、URL のパラメーターなどで切り替えます。何も付けずに開いたときは今のままで、案からは本物の保存に書きません。
- 触った人が決めたことを伝えたら、頼まれなくても、仕様書や票の「未決」を、決まった内容と理由に書き換えます。書くのは相手が言った範囲までで、AI の側に気がかり（決めた形に抜け道がある、など）が残るなら、決定と分けて1行書きます。「まだ決めない」と言われたら、今の見立てと、誰がいつ決めるかを書きます。
- 試作の行き先は自分で決めます。既定は、main に入れず、試作と分かる名前のブランチにコミットし、決定を書いた文書にそのブランチの名前を書く形です（あとで試作を開き直せます）。ブランチを push していなければ、手元だけにあることを返事と文書に書きます。main へのコミットは、頼まれていなければしません。
- 決まった案を本番に入れるときは、試作のコードをそのまま移さず、試作で省いていたもの（保存など）を本番のやり方で書き、落ちた案と切り替えの仕組みを消し、何に決めたか・なぜかを残します。

## 参考にした公開の Skill

書く前に、skills.sh で多く入れられている [mattpocock/skills](https://github.com/mattpocock/skills) の prototype（MIT ライセンス。2026年11月の skills.sh のインストール数は約108万）を読みました。文は写していません。

| 取り入れた所 | 取り入れなかった所 |
|---|---|
| 試作は1つの問いに答える捨てるコード、問いが動きか見た目かで作る物を分ける、画面の案は今のページの中で URL のパラメーターで切り替える、案は構造で違える、試作は main に入れずブランチに残して決定から引く | 動きの試作の HTML の細かい組み立て方（自由に押すボタンとタブごとの手引き）、切り替えのバーの作り（矢印キーなど）の指定。試した範囲では、AI は言われなくても十分な試作を作ったので、作り方の細部は書いていません |

元の Skill は試作の作り方が中心です。この Skill は、試した AI が外した所（決まったことを聞かずに文書に書く、相手が言っていない理由を足さない、main へのコミットの扱い）に重みを置いています。同じ場面で元の Skill を読ませた結果は、下の「試した結果」の表にあります。

## 試した結果

2026年11月に、架空の場面で試しました。作業する AI（Claude の Sonnet）は、git のリポジトリの中で作業します。頼む人の役は別の AI が、決めた設定のとおりに演じました。記録は、Skill の有無を伏せて、別の AI（Claude の Opus）が採点しました。作った HTML は、作業する AI に見えない検査でブラウザーに開き、エラーが出ないか、（場面3は）設定が開き直しても残るかを見て、採点に渡しました。場面ごとに守ってほしいこと（観点）を決め、それぞれを満たしたかを見ました。

- 場面1：貸し会議室の予約の状態の案（仮予約の失効、日程変更、キャンセル料）を試作する。仕様書に未決が2点ある。試作を渡したあと、頼んだ人が2点を決めて「本実装は来週。今日はここまで」と言う。観点は7個。
- 場面2：設定画面の通知の欄（チェックボックスが12個）の見せ方の案を見比べる。案を渡したあと、頼んだ人が「2つ目が良さそう。決めるのは来週チームで」と言う。観点は6個。
- 場面3：3案の試作が入ったリポジトリで「B 案に決めた。本番にして」と頼む。試作の B 案は保存をしていない。観点は6個。
- 場面4：「この関数に 23:53 を渡すとどうなるか、ちょっと試して教えて」と頼む。落とし穴の無い場面で、Skill を入れたせいで試作を作り始めたり重くなったりしないかを見る。観点は3個。

観点は、たとえば場面1なら「何を確かめる試作かを書いた」「開発者でない人が触れる」「決まった2点を文書に書き残した」「試作の行き先を決めた」のようなものです。表の数字は、満たした観点の数を3回分足したものです。分母は観点の数×3回です。採点は観点ごとに「満たした・一部だけ・満たさない」の3段で、表は「満たした」だけを数えています。観点は Skill の書き手が決めたもので、観点ごとの重みは同じに置いています。

| 場面 | Skill なし | 元の prototype を読ませる | この Skill を読ませる |
|---|---|---|---|
| 1 予約の状態の試作と、決まったあと | 15/21 | 16/21 | 21/21 |
| 2 設定画面の案と、まだ決めないと言われたあと | 13/18 | 13/18 | 18/18 |
| 3 決まった案を本番に入れて片付ける | 15/18 | 16/18 | 18/18 |
| 4 関数をちょっと試す（落とし穴なし） | 6/9 | 7/9 | 9/9 |

- 右の2列は、それぞれの Skill の本文を必ず読ませた条件です。場面は、Skill なしの外し方を見てからこの Skill を書いたので、この Skill がその場面に合わせて書かれている分、数字は甘く出ている可能性があります。場面も観点もこの Skill の書き手が決めたもので、元の prototype が力を入れている所（試作の画面の組み立て方、切り替えのバーの作り）は観点に入っていません。
- 元の prototype を読ませると、試作の作りは Skill なしと同じく良く、場面2では3回とも今の設定画面の中に案を出しました。一方で、決まった2点を仕様書に書かない回が3回中2回あり、試作のブランチは「その想定です」と言うだけで作りませんでした。場面2では3回とも、何も付けずに開くと案 A が出て今の画面が変わり、少なくとも2回は案の操作が本物の設定を書き換えました。場面1は1回あたり 0.37〜0.41 ドルで、この Skill（0.20〜0.22 ドル）の2倍近くかかりました。
- この Skill の列は、初版で見つかった踏み越えを直した版の数字です。初版は場面1で、決定を書くときに相手が言っていない了解（「この抜け道は承知のうえ」）を3回とも足し、場面2で、頼まれていない文書を main に2回コミットしました。本文を直した版では、どちらも出ませんでした。初版の数字は、場面1から順に 18/21、18/18、18/18、9/9 です（場面1の欠けは、試作をブランチに移したため検査が HTML を見つけられなかったもので、検査を直しました）。
- Skill を置くだけにして、読むかどうかを AI に任せた条件も試しました（作者が使っているほかの Skill 31本と一緒に置いた状態、直した版）。場面1〜3の6回はすべてこの Skill を読み、場面1が 13/14、場面2が 12/12、場面3が 12/12 でした。場面4（落とし穴なし）の2回は読まずに、6/6 でした。
- 場面4の Skill なしで欠けた3つは、3回とも同じ観点（軽さ）で、理由と直し方の案まで書いて報告が長くなったものです。関数は3回とも正しく動かして答えています。Skill を読まなかった「置くだけ」の2回は短く答えたので、回ごとのばらつきと見ています。Skill が罠の無い場面の点を上げたとは言えません。
- 1回の費用（Skill なし → あり）は、場面1が 0.16〜0.24 → 0.20〜0.22 ドル、場面2が 0.16〜0.17 → 0.19〜0.27 ドル、場面3が 0.05 → 0.07 ドル、場面4が 0.02 → 0.02〜0.03 ドルでした。4つの場面とも、ほぼ変わりません。落とし穴の無い場面4の時間は、Skill なしで19〜23秒、ありで17〜19秒でした。
- 場面ごとに3回ずつで、数は少ないです。試作を人が実際に触って決める所は、決まった台詞を返す AI で代えています。画面の案の見た目の良し悪しは採点していません。React などの枠組みを使うアプリ、作業する AI が Sonnet 以外のとき、Claude Code 以外のツールで読み込まれるかは、確かめていません。

## 入れ方

```
npx skills add itoken-lab-jp/skills -g --skill prototyping
```

`-g` は、プロジェクトごとではなく、自分のユーザーのどのプロジェクトでも使える場所に入れる指定です。手順の本文は [SKILL.md](../skills/prototyping/SKILL.md) です。入れ方の詳しい説明（置かれる場所、ツールごとの違い）は [README](../README.md#入れ方) にあります。
