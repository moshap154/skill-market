# japanese-translation

AI に英語のリリースノートを「社内向けに日本語にして」と頼むと、一文ずつは自然な日本語が返ってきます。架空の場面で Skill を入れない AI に試させると、条件と数字は落とさず、「〜することができます」のような直訳の型もほとんど残しませんでした。外したのは、読み手に合わせる所と、画面の名前・用語と確からしさの扱いです（下の「Skill を入れずに頼むと」）。原文の段落の順のまま訳し、「一般の利用者は何もしなくてよい」「管理者がすること」を書き分けませんでした。英語の画面の名前を日本語に置き換えたので、読み手は英語の画面でその項目を探せません。なじみの薄いカタカナ語も多めでした。また、確定していない「expect」（見込み）を「予定」と訳し、決まったことのように読める訳にした回がありました（料金の知らせの場面では3回とも）。

japanese-translation は、英語などの文章を AI に日本語に訳させるときの、AI が読む手順書（Skill）です。Skill は、エージェントが作業に合わせて読み込む手順書のファイルです。訳すのは、日本語の読み手が原文の読み手と同じことを分かり、同じことができるようにするためなので、読み手と用途で訳し方を決めさせます。社内に回すお知らせやリリースノートは、原文の事実を全部残したうえで「誰が何をするか」が分かる形に組み直させます。契約や規約は、原文の構成に沿って訳させます。

向いているのは、海外のサービスのお知らせ・リリースノート・ヘルプ・メール・規約を、Claude Code や Codex などのエージェントに訳させて、社内に回したり確認に使ったりする人です。会社に訳語の一覧や翻訳の決まりがあれば、そちらを先に読ませます。

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。入れておくと、エージェントは Skill の説明文（どんなときに読むか）を見て、次のような頼みで読み込みます。

- 「このリリースノート、社内の利用者向けに日本語にして」
- 「ベンダーから来た英語のメール、経理と各部署に回したいので訳して」
- 「契約書の第7条を、法務の確認用に訳して」

確実に読ませたいときは「japanese-translation の Skill に従って」と名前で頼みます。社内に回す訳では、回す相手と自社の事情（人数・契約の形・使っている機能）を頼みに書くと、それに当てはめた要点を訳の先頭に置きます。

## Skill を入れずに頼むと

架空の場面で、Skill を入れない AI に同じ頼みを3回ずつさせました（場面の中身と数え方は、下の「試した結果」）。

- 英語のリリースノートを社内の利用者向けに訳す場面では、3回とも原文の段落の順のまま訳しました。一般の利用者は何もしなくてよいこと、通知をオンにするのは管理者であること、API の節は API を使う人だけの話であることを、3回とも書き分けませんでした。設定の場所は3回とも日本語に置き換え、英語の画面の名前を添えませんでした。「スケジュールエクスポート」「リトライ」のような、英語を読まない人になじみの薄いカタカナ語も多めでした。宣伝の強めの「significantly」は、数字の裏付けが無いまま3回とも「大幅に向上」と訳し、「expect」を「予定」と訳した回が1回ありました。条件と数字（最大3回・10分おき・2027年3月31日など）は3回とも落としませんでした。
- 英語の料金の変更の知らせを社内に回すために訳す場面（Skill の最初の版を書いたあとに作った場面）では、3回とも「Admin Console」を「管理コンソール」に置き換え、3回とも新しいプランの「見込み」を「予定」と訳しました。経理と各部署に何が関係するかを先に書いた回はありませんでした。
- 契約の条文を法務の確認用に訳す場面では、3回とも条文の構成に沿い、義務（shall、〜するものとする）と権利（may、〜できる）を訳し分けました。この場面は Skill が無くてもできていて、Skill を入れたせいで要点にまとめたりしないかを見るために置いています。

## SKILL.md に書いてあること

AI が読むファイルです。使うだけなら読まなくてかまいません。どう動くかを確かめたいときは [SKILL.md](../skills/japanese-translation/SKILL.md) を開いてください。

- 訳す前に、誰が・どこで・何のために読むかと、原文にどこまで沿うかを用途で決めます。契約・規約・仕様は構成も原文に沿い、補足は訳注に分けます。お知らせ・リリースノート・社内向けの案内は、原文の事実を全部残したうえで、読み手の中で行動が違えば「誰が何をするか」を先に置きます。原文に無い手順・約束・依頼は足しません。
- 条件・数字・範囲・期限・対象を原文から書き出して訳と照らします。will・expect・may・should・must の強さを変えず、宣伝の強め（significantly・excited）は、数字の裏付けが無ければ強めずに訳します。
- 画面の名前は、日本語の表記を確かめられなければ原文を残して訳を添えます（「Billing > Invoices（請求 > 請求書）」）。製品名・コマンド・API・エラーの番号は原文のまま。カタカナ語は読み手がふだん使う語に限り、同じ原語は同じ訳語にそろえます。
- 訳したあと、原文と訳を1文ずつ照らし、落ちた条件と足した説明が無いかを見ます。分からない語は推測で決めずに印を付けて報告します。

## 参考にした公開の Skill

skills.sh で翻訳の Skill を探しましたが、2026年11月の時点でいちばん多く入れられている [jimliu/baoyu-skills](https://github.com/jimliu/baoyu-skills) の baoyu-translate でも約2.6万で、上位の Skill（数十万〜百万）と比べると少数でした。baoyu-translate は、訳の速さと丁寧さの3つの段階、長い文書を分けて訳すときの用語の一覧が中心です。この Skill は、外し方を見てから書き、読み手と用途で訳し方を決める所、確からしさの強さ、画面の名前の扱いを中心にしました。文は写していません。

## 試した結果

2026年11月に、架空の場面で試しました。作業する AI（Claude の Sonnet）は、原文のファイルを置いたフォルダーの中で作業します。頼む人の役は別の AI が、決めた設定のとおりに演じました。記録は、Skill の有無を伏せて、別の AI（Claude の Opus）が採点しました。場面ごとに守ってほしいこと（観点）を決め、それぞれを満たしたかを見ました。

- 場面1：英語のリリースノート（失敗したときの再試行、管理者への通知、旧 API の廃止、SFTP は対象外）を、英語を読まない社内の利用者向けに訳す。観点は6個。
- 場面2：英語の料金の変更の知らせ（次の更新から1席あたり月10ドル→12ドル、5席未満は対象外、年払いは15%引き、新しいプランは見込み）を、経理と各部署に回すために訳す。頼む人は、自社が40人で月払いであることを、聞かれたら答えます。Skill の最初の版を書いたあとに作った場面ですが、2回目と3回目の直しにもこの場面の外しを使いました。観点は6個。
- 場面3：契約の条文（解約後のデータの削除と、その例外）を、法務の確認用に原文に沿って訳す。組み直してはいけない場面で、Skill を入れたせいで要点にまとめたりしないかを見ます。観点は3個。

観点は、たとえば場面1なら「条件と数字を全部残す」「一般の利用者・管理者・API を使う人のそれぞれに関係のあることが分かる」「画面の名前は原文を残すか添える」、場面2なら「見込みを確定の予定にしていない」「原文に無い手順や判断を足していない」のようなものです。表の数字は、満たした観点の数を3回分足したものです。分母は観点の数×3回です。採点は観点ごとに「満たした・一部だけ・満たさない」の3段で、表は「満たした」だけを数えています。観点は Skill の書き手が決めたもので、観点ごとの重みは同じに置いています。独立に試したのは場面ごとに3回です。

| 場面 | Skill なし | Skill あり |
|---|---|---|
| 1 リリースノートを社内向けに訳す | 8/18 | 17/18 |
| 2 料金の変更の知らせを社内に回す（Skill の最初の版のあとに作った場面） | 6/18 | 14/18 |
| 3 契約の条文を原文に沿って訳す | 9/9 | 8/9 |

- 「Skill あり」は、Skill の本文を必ず読ませた条件です。場面1と場面3は2回目の版、場面2は3回目の版の数字です。3回目の版は、2回目に足した「要点を先に置く」の行に「要点に依頼を足さない」を足しただけです。最初の版の数字は、場面1・2・3が 17/18・15/18・9/9 でした。最初の版では、場面2で「誰が何をするか」の要点を3回とも置かず、置くかを頼む人に聞き返しました。そのため2回目の版で、社内に回す訳では要点を聞き返さずに置く、を足しました。2回目の版では要点を置くようになりましたが、1回は「経理部は予算に反映してください」という原文に無い依頼を足しました。直すのに使った場面で測っているので、表の数字は甘く出ている可能性があります。
- Skill ありで残った外しは、次のとおりです（「一部だけ」と採点されたものも含めて全部）。場面1の1回は、「significantly」を「大きく向上」と訳し、宣伝の強さを残しました。場面2では、自社の人数を頼む人に聞かずに「伺っていない」と報告し、5席未満の例外が自社に当たらないことも、各部署は何もしなくてよいことも書きませんでした（3回とも）。場面2の1回は、「world-class」を「世界水準」と宣伝の言い方のまま訳しました。場面3の1回は、「willful misconduct」を「故意の違法行為」と訳し、原文に無い「違法」を足しました。
- 落とし穴の無い場面は、翻訳では試していません。場面3は、組み直してはいけない場面として、Skill が余計なことをさせないかの確かめを兼ねています。
- Skill を置くだけにして、読むかどうかを AI に任せた条件（ほかの Skill 33本と一緒に置いた）も試しました。場面1〜3の5回とも japanese-translation を読み、場面1は 12/12（2回）、場面2は 9/12（2回）、場面3は 3/3（1回）でした。場面2の外しは、上の Skill ありと同じ2つ（自社の人数を聞かずに要点を置く、を2回、「world-class」を「世界水準」と訳す、を1回）です。
- 1回の費用（Skill なし → あり）は、場面1が 0.02 → 0.03〜0.05 ドル、場面2が 0.02 → 0.03〜0.09 ドル、場面3が 0.02 → 0.03〜0.04 ドルでした。時間はどれも 20秒前後で、聞き返した回だけ 50秒ほどでした。
- 試したのは英語から日本語だけです。作業する AI が Sonnet 以外のとき、Claude Code 以外のツールで読み込まれるかは、確かめていません。

## 入れ方

```
npx skills add itoken-lab-jp/skills -g --skill japanese-translation
```

`-g` は、プロジェクトごとではなく、自分のユーザーのどのプロジェクトでも使える場所に入れる指定です。手順の本文は [SKILL.md](../skills/japanese-translation/SKILL.md) です。入れ方の詳しい説明（置かれる場所、ツールごとの違い）は [README](../README.md#入れ方) にあります。
